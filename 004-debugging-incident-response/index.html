Complex Failure Diagnosis

Isolating Multi-Turn, Multi-Agent, and Tool Failures

MENTAL MODEL

The Four-Layer Failure Isolation Framework

Live Read-Along (click any sentence to jump)
When a multi-turn or multi-agent Claude system breaks in production, resist the urge to start tweaking prompts. First, isolate the failing trace into one of four layers: model output, the agent harness, tools and M C P servers, or retrieval data. Pinpointing the exact boundary turns a non-deterministic mystery into a concrete engineering bug.

Production failures in multi-turn and multi-agent Claude systems rarely stem from a single obvious exception. Non-deterministic outputs, stateful histories, and asynchronous tool loops blur symptoms across boundaries. Before touching a prompt, isolate the failing span into one of four distinct layers: model output (refusals, truncation, reasoning drift), agent harness (history mutation, buffer limits, retry logic, compaction loops), tools and MCP (schema ambiguity, protocol mismatches, transport errors), or data and retrieval (stale chunks, missing context, indirect prompt injection).

EXAM TRAP

Indirect Prompt Injection False Alarms & Silent Structured-Output Failures

Live Read-Along (click any sentence to jump)
Watch out for two classic exam traps. If Claude flags your own tool output as a prompt injection, it is because your harness put instructions inside the tool result block instead of keeping it pure data. Second, in the Agent S D K, a run can return subtype success while structured output is null. Always treat that as a failure and check for a refusal stop reason or contradictory schema constraints.

Two subtle production traps: First, if Claude refuses to act on a tool result or asks the user to confirm instructions from it, check whether your harness placed your own instructions inside the tool_result content. Claude is trained to treat instructions inside tool results as untrusted third-party content (indirect prompt injection). Keep tool_result strictly data-only, and send harness instructions in a subsequent user turn or a mid-conversation role: "system" message.

Second, in the Agent SDK, a result can finish with subtype: "success" while structured_output is None (Python) or undefined (TypeScript). Always treat this as an application failure and inspect two causes: stop_reason: "refusal" or contradictory JSON Schema constraints (such as minLength exceeding maxLength).

HARNESS & SDK TRIAGE

Diagnosing Agent SDK and Claude Code Runtime Failures

Live Read-Along (click any sentence to jump)
When debugging the Agent S D K or Claude Code, know the exact runtime failure signatures. In Python, Process Error hides real standard error unless you register a stderr callback, and large P D F reads trigger C L I J S O N Decode Error at one megabyte because base sixty-four payloads are duplicated—fix it by raising max buffer size and resuming the session. In Claude Code, run slash context, slash doctor, and safe mode to isolate configuration overrides and autocompact thrashing.
  • Subprocess startup & security refusals: CLINotFoundError signals missing PATH or bad cli_path; on Windows, Python Agent SDK raises CLIConnectionError and refuses .bat/.cmd shims (like claude.cmd) to prevent cmd.exe argument injection—use a native claude.exe.
  • Process exits & stderr capture: In Python, ProcessError hides real CLI stderr behind placeholder text unless you pass a stderr callback in ClaudeAgentOptions; catch ResultError (a subclass of ProcessError) first when the CLI emitted an error result.
  • Buffer overflows on large tool payloads: CLIJSONDecodeError occurs when a single message exceeds the 1 MB default max_buffer_size—common on PDFs (~393 KB+) and screenshots because base64 is stored twice. Increase max_buffer_size (e.g., 64 * 1024 * 1024), call disconnect(), and resume via resume=session_id.
  • Silent streaming aborts: In Python, an exception inside an async prompt generator terminates the query() loop without raising, logging Prompt stream failed; closing stdin; wrap the generator in try/except to surface tracebacks.
  • Claude Code config & thrashing: Use /context, /doctor, /hooks, /mcp, and claude --safe-mode to isolate config overrides (settings.local.json beats settings.json; hooks live in settings.json, never standalone files). Recover from Autocompact is thrashing by chunking large reads, delegating to a subagent, or running focused /compact.
MANAGED AGENTS & WORKERS

Troubleshooting Self-Hosted Managed Agent Workers

Live Read-Along (click any sentence to jump)
For self-hosted Managed Agents, start with the work stats endpoint from external ops tooling. Sustained non-zero pending counts point to a stalled worker, while zero workers polling flags connectivity or credential issues. Watch for silent memory-store mount failures: the session sits idle with requires action and no error event until you fix the host mount and send a user interrupt.
  • Inspect queue telemetry first: Poll GET /v1/environments/{environment_id}/work/stats (with your organization API key from ops tooling, never on the worker host) to read depth (unclaimed backlog), pending (claimed but unacknowledged—sustained non-zero means a stalled worker), oldest_queued_at, and workers_polling (liveness over the last 30 seconds).
  • Silent memory-store mount failures: If a worker cannot mount a memory store (e.g., missing session secret, unwritable /mnt/memory, or leftover directory from a killed worker), it fails the work item while the session sits idle with requires_action and no error event. Fix the host path, then send a user.interrupt event to requeue and retry.
  • Graceful teardown vs. hard kills: POST .../work/{work_id}/stop transitions work to stopping so the worker cancels in-flight tools and syncs memory edits; force: true only marks the item stopped immediately without ending the in-flight tool sooner. Give containers enough SIGTERM grace period (60s, or 210s for Python workers) so memory syncs complete.
Complex Failure Diagnosis

Debugging Thinking, Refusals, Grounding, and MCP

PRESERVED THINKING

Preserved-Thinking Prefix Checks and 400 Errors

Live Read-Along (click any sentence to jump)
On models with preserved thinking, every thinking block signature fingerprints the exact system prompt, tools list, and messages that came before it. Even changing a single date in the system prompt at midnight invalidates every thinking block after it. That triggers a four hundred error saying the block is bound to a different conversation—or worse, lets mismatched reasoning reach the model silently if you are not logging input transformations.

Models with preserved thinking—including Claude Opus 5.5, Sonnet 5.5, Haiku 5.5, and Fable/Mythos 5.1+—cryptographically bind each thinking block's signature to its exact prefix: system, tools, and all preceding messages. If your harness rebuilds system with a rolling timestamp, mutates the tools array mid-conversation, injects and later removes a per-turn reminder, or runs client-side compaction while keeping recent thinking blocks, the prefix check fails. Depending on the model, the API either rejects the call with HTTP 400 (Invalid signature in thinking block. The block is bound to a different conversation.) or silently passes stale reasoning to Claude unless you monitor input_transformations.

RECOVERY PATTERN

Immediate Mitigation vs. Append-Only Architecture

Live Read-Along (click any sentence to jump)
To recover an already-broken conversation immediately, send the thinking binding controls beta header with prefix mismatch behavior set to drop block, and persist that setting for that session. Never leave drop block on globally to hide bugs, because dropping thinking costs extra output tokens and breaks the prompt cache. The permanent fix is an append-only history: echo assistant turns verbatim, freeze system and tools, and append updates at the end.
# 1. Immediate recovery for an affected in-flight conversation ONLY:
response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={
        "type": "adaptive",
        "block_binding": {"prefix_mismatch_behavior": "drop_block"},
    },
    messages=messages,
    betas=["thinking-binding-controls-2026-08-01"],
)
# Inspect response.input_transformations for reason == "prefix_binding_mismatch"

# 2. Permanent fix — Three Habits of an Append-Only Integration:
#    (a) Echo assistant turns verbatim (including thinking blocks with empty text when display="omitted").
#    (b) Build `system` and `tools` once per conversation and never mutate them.
#    (c) Append updates at the end via new user turns or mid-conversation role="system" messages;
#        use server-side compaction/context editing instead of client-side trimming.

REFUSALS & GROUNDING

Model Refusals as a Failure Class and Stage-by-Stage Grounding Triage

Live Read-Along (click any sentence to jump)
Refusals are not transient network errors—they arrive as H T T P two hundred with stop reason refusal and a category in stop details. Because policy checks inspect the entire transcript, retrying in the same conversation just loops the refusal; you must rewind, start fresh, or use server-side fallback. For retrieval-grounding bugs, trace stage by stage from query formulation through recall, reranking, and context assembly before blaming synthesis.

Treat refusals as a first-class failure mode, never an HTTP error: Classifier refusals return HTTP 200 with stop_reason: "refusal" and stop_details.category (such as cybersecurity safeguards or reasoning_extraction when a prompt or CLAUDE.md asks for verbatim <thinking> scratchpads). Because Usage Policy checks evaluate the entire conversation, retrying in-thread usually re-triggers the refusal. Rewind before the triggering turn (/rewind) or start a clean session; for API workloads, route declined categories via fallbacks: "default" (anthropic-beta: server-side-fallback-2026-07-01) or client-side fallback middleware.

Isolating retrieval-grounding failures by stage: When a RAG or search-grounded agent hallucinates or omits facts, inspect each pipeline stage in order—(1) query formulation/expansion, (2) index recall and chunk boundaries, (3) reranker top-K cutoffs, (4) context window truncation or stale documents, and (5) model synthesis faithfulness against the exact retrieved chunks.

MCP DEBUGGING

Debugging MCP Servers, Inspector, and Tunnel Stacks

Live Read-Along (click any sentence to jump)
When an M C P integration misbehaves, reach for the M C P Inspector first to decouple the server from the host client. On local stdio servers, logging to standard out corrupts J S O N R P C framing, so always log to standard error or OpenTelemetry. For M C P tunnels, debug strictly in layer order: outbound cloudflared connectivity, inner T L S certificates, and finally upstream I P validation and routing.
  • Start with MCP Inspector: Run npx @modelcontextprotocol/inspector in --web, --cli (scriptable for CI), or --tui mode to isolate server behavior from host client quirks.
  • Never log to stdout on stdio servers: Local stdio servers use stdout exclusively for JSON-RPC framing; write logs to stderr (captured automatically by the host) or OpenTelemetry. Always use absolute paths and explicit env blocks in config because stdio servers inherit a minimal environment and undefined working directory.
  • Decode JSON-RPC protocol errors: Call server/discover to verify version negotiation. Error -32022 is UnsupportedProtocolVersionError; -32021 is MissingRequiredClientCapabilityError; -32602 often signals missing required per-request _meta fields (io.modelcontextprotocol/protocolVersion or clientCapabilities).
  • Layer-by-layer MCP tunnel triage: Diagnose in order: (1) outbound cloudflared to tunnel edge (check TUNNEL_TOKEN and TCP/UDP port 7844), (2) inner TLS between Anthropic and your proxy (SAN must match *.<tunnel-domain> and CA must be registered), and (3) upstream routing & SSRF IP validation (proxy allows only RFC1918 IPv4 by default; setting upstream.allowed_ips replaces the default ranges).
Incident Response and Learning Loops

Triage, Mitigation, Rollback, and Communication

INCIDENT TRIAGE

Triaging Outages vs. Silent Quality Regressions

Live Read-Along (click any sentence to jump)
In production AI operations, the hardest incidents return H T T P two hundred while quality silently collapses. Start triage by checking status dot claude dot com, confirming which model and effort level actually served traffic, and slicing traces by stop reason, tenant, and deployment version. That immediately separates an upstream provider outage from a bad prompt release or data drift.

LLM production incidents fall into two operational classes: hard availability outages (HTTP 429 rate limits, 529 overloaded, 5xx errors, worker queue stalls) and silent quality regressions where endpoints return HTTP 200 while accuracy, refusal rates, latency, or token spend degrade sharply. Triage starts by scoping blast radius—check status.claude.com, confirm active model IDs (watching for automatic model fallback notices), verify effort levels and context saturation, and slice traces by release version, tenant, and stop_reason cohort to determine whether the trigger is external provider load, a recent prompt/tool deploy, or upstream data drift.

EXAM TRAP

Why Deterministic Rollback Beats Mid-Incident Prompt Tweaking

Live Read-Along (click any sentence to jump)
Here is a high-frequency exam principle: during an active quality regression, roll back to the last known-good versioned prompt, schema, or model snapshot before attempting any fix. Ad-hoc prompt patching in production is unverified, busts your prompt caches, and can trigger secondary prefix-check failures across live sessions.

Under incident pressure, teams are often tempted to edit the system prompt live to patch a refusal spike or hallucination. On the CCDV-P exam, rolling back to a verified versioned artifact (prompt, tool schema, model snapshot, or retrieval index) almost always beats ad-hoc hot-patching. Live prompt edits are uncalibrated, invalidate prompt caches across the fleet, can break preserved-thinking prefixes for active sessions, and frequently trade one regression for another.

STATEFUL ROLLBACK

Safe Rollback and State Preservation for Long-Running Agents

Live Read-Along (click any sentence to jump)
Rolling back stateful agents requires extra care. Pinning system prompts and tools per session lets you roll back new traffic without breaking preserved-thinking signatures on active sessions. And when recovering an individual bad turn, rewind to a clean checkpoint instead of correcting in-thread, while always preserving Request and Message I Ds for forensics.
  • Respect active session prefixes: Rolling back a global system prompt or tools list fixes new sessions immediately, but existing long-running conversations that resume with preserved thinking must either keep their original session-pinned system/tools or use per-session drop_block recovery.
  • Rewind rather than correct in-thread: When an agent produces a bad turn or triggers a refusal, correcting it in a follow-up message keeps the flawed attempt in context and anchors later turns. Roll back to a pre-failure checkpoint (e.g., /rewind or persisted session state).
  • Preserve forensic evidence before clearing: Before resetting queues, restarting workers, or clearing broken sessions, capture Request IDs, Message IDs, sanitized trace spans, and exact tool payloads so postmortem reconstruction is possible (respecting ZDR and PII redaction policies).
STAKEHOLDER COMMS

Communicating Clearly During Non-Deterministic Incidents

Live Read-Along (click any sentence to jump)
During a non-deterministic AI incident, disciplined communication keeps trust intact. Report verified blast radius, explain the active mitigation including any latency or quality tradeoffs from fallback routing, share concrete workarounds, and commit to a timestamp for the next update without guessing at root causes.

Effective incident communication separates confirmed facts from hypotheses. Status updates to engineering leadership, support teams, and customers should cover four elements: (1) concrete user-visible impact and affected scope (e.g., percentage of workflows or specific tenants), (2) active containment and any temporary tradeoffs (such as fallback model latency increases or read-only degradation), (3) clear customer workarounds (e.g., starting a fresh session after a policy refusal or escalating flagged tasks), and (4) the exact time of the next update. Never speculate on model-level root causes before trace cohorts confirm them.

Incident Response and Learning Loops

Converting Incidents into Evals, Monitoring, and Postmortems

LEARNING LOOPS

Closing the Production Reliability Loop

Live Read-Along (click any sentence to jump)
Shipping a hotfix never finishes an incident. Because prompts, tools, retrieval indexes, and models evolve constantly, unguarded bugs always return. Before closing any production incident, convert it into three permanent artifacts: a C I regression evaluation, monitoring coverage for the blind spot, and a blameless postmortem with owned action items.

Fixing the immediate bug that caused an LLM outage is only half the job. Because model behavior, prompt templates, MCP tool lists, and retrieval corpora evolve continuously, any failure mode without an automated guard will eventually regress. A complete incident learning loop produces three durable engineering artifacts before the incident ticket closes: (1) new regression evaluation cases in the CI/CD gate, (2) expanded production monitoring and alerting covering the blind spot that delayed detection, and (3) a blameless postmortem documenting systemic contributing factors and owned follow-up work.

INCIDENT-TO-EVAL

Turning Production Traces into Durable Regression Evals

Live Read-Along (click any sentence to jump)
Promote every real incident trace into your test suite, after sanitizing P I I and secrets. Match the test to the failure layer: harness contracts like tool-result ordering and prefix invariance belong in fast deterministic C I tests, while grounding and refusal regressions belong in your calibrated evaluation suite—always covering compaction, fallback, and session resume.
  • Sanitize before promoting to golden sets: Strip PII, credentials, and customer secrets from failing production traces (honoring zero-data-retention commitments) while preserving the exact structural trigger—such as the tool schema, multi-turn history shape, or retrieved chunk set.
  • Match test type to failure layer: Harness and contract bugs (missing tool_result, JSON escaping, buffer limits, prefix mutations) belong in fast deterministic CI tests. Quality, grounding, and refusal regressions belong in calibrated eval suites (code-graded checks plus human-calibrated LLM-as-judge rubrics).
  • Exercise edge-case lifecycle paths: Plain single-turn happy-path tests miss real production bugs. Include multi-turn sessions that trigger compaction, late tool loading, model fallback, and session resume.
CI REGRESSION GATE

Enforcing Preserved-Thinking Prefix Invariants in CI

Live Read-Along (click any sentence to jump)
Anthropic recommends a two-step pattern for testing preserved-thinking invariants in C I. First, prove your test can fail by intentionally mutating the system prompt with drop block and asserting a prefix binding mismatch entry. Then remove the mutation and run real compaction and resume flows with prefix mismatch behavior set to error so any future regression breaks the build.
# Step 1: Prove the CI harness catches a real violation by injecting a deliberate prefix
# change with `drop_block` and asserting `prefix_binding_mismatch` appears.
# Step 2: Remove the deliberate change and enforce `prefix_mismatch_behavior="error"`
# across compaction, late-tool, and session-resume integration tests.
response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={
        "type": "adaptive",
        "block_binding": {"prefix_mismatch_behavior": "error"},
    },
    messages=session_messages,
    betas=["thinking-binding-controls-2026-08-01"],
)
# Fail CI only on reason == "prefix_binding_mismatch" (ignore expected
# "model_binding_mismatch" entries in deliberate cross-model fallback tests).
MONITORING COVERAGE

Eliminating Observability Blind Spots Found in Triage

Live Read-Along (click any sentence to jump)
Every minute spent hunting for clues during triage reveals a monitoring gap. Add alerts on stop reason distributions—especially refusals and max tokens—not just H T T P status codes. Log input transformations for silent thinking mismatches, watch prompt-cache hit rates for prefix drift, and emit explicit metrics whenever fallback models activate.
  • Alert on stop_reason distribution shifts: Track rolling rates of refusal (segmented by stop_details.category), max_tokens, pause_turn, and model_context_window_exceeded—not just HTTP 4xx/5xx error codes.
  • Watch silent reasoning and cache loss: Log input_transformations (alerting on thinking_mismatch_allowed or unexpected thinking_dropped) and alert on sudden drops in cache_read_input_tokens that signal prefix mutations.
  • Track fallback activation and worker health: Emit explicit metrics whenever server-side or client-side fallback routes traffic to a secondary model, and alert on Managed Agents pending > 0 sustained stalls, workers_polling == 0, and rising oldest_queued_at age.
BLAMELESS POSTMORTEM

Writing Blameless Postmortems for Probabilistic Systems

Live Read-Along (click any sentence to jump)
Finally, write blameless postmortems that target systemic weaknesses rather than individuals or vague model flakiness. Document why the bad change reached production—like a missing evaluation gate, an unpinned M C P tool list, or an undifferentiated retry loop—and assign time-bound engineering fixes tied directly to your S L O error budget.

A strong CCDV-P postmortem never stops at "the model hallucinated" or "an engineer shipped a bad prompt." It identifies systemic gaps—such as an undifferentiated retry path that retried refusals, a missing CI evaluation gate, an unpinned MCP tool list that mutated mid-session, or a missing deterministic guardrail—and pairs each finding with a concrete, owner-assigned, time-bound remediation prioritized against your quality and availability SLO error budget.

CCDV-P Scenario Practice

Production Scenario Questions

Scenario 1: Midnight 400 Spike on Preserved-Thinking Sessions

A long-running multi-turn coding assistant running on Claude Opus 5.5 operates smoothly all day, then at 00:00 UTC active conversations suddenly fail with HTTP 400: `messages.3.content.0: Invalid signature in thinking block. The block is bound to a different conversation.` Investigation reveals the agent harness rebuilds the `system` prompt on every turn using the current UTC date. Active customer sessions are currently blocked. What is the best two-step response?

Answer: B — B follows Anthropic's exact two-step recovery and permanent fix: `drop_block` (with `thinking-binding-controls-2026-08-01`) unblocks already-mutated in-flight conversations, while making the integration append-only (freezing `system` and appending date updates in a new turn or mid-conversation system message) prevents future prefix-check failures and preserves prompt caching. A fails because retrying an unchanged invalid body always returns 400 and stripping all thinking globally degrades reasoning quality; C fails with a 400 error because thinking is always on for Claude Opus 5.5; D masks an ongoing bug, increases output token spend every turn, and repeatedly invalidates prompt caches.

Scenario 2: Silent None Structured Outputs and 1 MB Buffer Aborts in Agent SDK

A document-processing pipeline built on the Python Claude Agent SDK experiences two failures in production: 15% of runs complete with `subtype: "success"` but `structured_output` is `None`, crashing downstream consumers; another 5% of runs processing 500 KB PDFs abort with `CLIJSONDecodeError: JSON message exceeded maximum buffer size of 1048576 bytes`. Which set of fixes addresses both root causes?

Answer: A — A directly resolves both documented Agent SDK failure modes: `subtype: "success"` with `structured_output: None` occurs on `stop_reason: "refusal"` or unsatisfiable schemas (e.g., contradictory `minLength`/`maxLength`) and must be handled as a failure in application code; `CLIJSONDecodeError` happens on ~393 KB+ PDFs because Read tool results encode base64 twice, exceeding the 1 MB default `max_buffer_size`—raising `max_buffer_size` (e.g., to 64 MB), disconnecting, and resuming via `session_id` fixes and recovers it. B catches the wrong exception and fails to fix buffer limits or schema/refusal causes; C abandons schema validation and doesn't stop the Read tool payload from exceeding 1 MB; D confuses interactive CLI debugging flags and effort with tool-result size.

Scenario 3: Post-Release Refusal Surge Masked by HTTP 200s

Thirty minutes after deploying a new prompt template for a customer support agent, HTTP 5xx alerts remain silent, yet customer escalations triple. Trace cohort analysis shows `stop_reason: "refusal"` jumped from 0.2% to 24% with `Details: [reasoning_extraction]` because the new template instructs Claude to output a verbatim `<thinking>` scratchpad field in its JSON response. Worse, the harness retry middleware retries refused turns three times inside the same conversation, tripling token spend. What should the on-call engineer do?

Answer: B — B executes the complete CCDV-P incident response and learning loop: immediate rollback to the last known-good prompt stops customer impact deterministically; fixing the undifferentiated retry path stops wasted retries on `stop_reason: "refusal"` (which re-triggers on the same conversation history); and adding both a CI regression eval and a `stop_reason: "refusal"` SLI alert prevents recurrence and eliminates the HTTP-200 blind spot. A hot-patches an unverified prompt that still triggers `reasoning_extraction` safeguards and worsens the retry storm; C invents a nonexistent capability; D prolongs an active 24% failure outage.
