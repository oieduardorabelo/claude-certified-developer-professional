### Q1 — Domain 2: Production Integration & Reliability

#### Question
A production support service runs on the first-party Anthropic API using prompt caching, extended thinking, and strict structured outputs. During a regional capacity event, the team's automated failover routes traffic to Amazon Bedrock and retries *any* response whose `stop_reason` is not `end_turn` with exponential backoff. Immediately after failover, a wave of requests fails with HTTP `400` schema/parameter errors on Bedrock, while other requests loop repeatedly on `max_tokens` and `refusal` responses, spiking cost and latency.

Which change best resolves the root causes?

- **A.** Increase Bedrock provisioned throughput and add jitter to exponential backoff so retried requests converge cleanly.
- **B.** Branch handling by `stop_reason` (retry only transient `429`/`5xx`, handle `max_tokens` and `refusal` on dedicated paths) and translate/normalize platform-specific feature parity in the failover adapter before routing to Bedrock.
- **C.** Remove extended thinking and structured outputs from the primary first-party API path so both providers share an identical minimal request schema.
- **D.** Fail over real-time traffic to the Message Batches API during capacity events so rate limits never trigger retries.

#### My Answer
**B** — Correct

#### Review
- **Why B wins:** Two distinct failure classes are colliding: (1) an undifferentiated retry loop that retries `max_tokens` (reproduces truncation & wastes tokens) and `refusal` (repeats a safety decline instead of routing to a safety-handling path), and (2) cross-platform feature/parameter parity differences between the first-party Anthropic API and Bedrock (`400` errors on unsupported beta headers or differing field formats).
- **Why others fail:** Jitter/throughput (**A**) does not fix `400` schema mismatches or bad retry logic; stripping features from primary traffic (**C**) degrades quality unnecessarily; Message Batches (**D**) is asynchronous (up to 24h), not suitable for real-time failover.

### Q2 — Domain 1: Advanced Agent Architecture & Context Management

#### Question
A long-running agent on the Messages API uses preserved thinking and prompt caching across 25+ turns. Mid-conversation (around turn 15), the orchestration harness updates the top-level `system` prompt with newly discovered workflow rules and appends 18 newly relevant tool definitions to the `tools` array. Immediately afterward, prompt cache hit rate collapses from ~90% to 0%, and multiple sessions fail with HTTP `400` thinking-block prefix validation errors.

What is the best architectural fix?

- **A.** Strip all historical `thinking` blocks from the conversation before every turn so the API skips prefix validation.
- **B.** Keep the top-level `system` prompt and `tools` prefix immutable for the session, inject mid-conversation instruction updates by appending new messages, and use deferred tool discovery (`tool_search`) rather than mutating the `tools` array mid-run.
- **C.** Reduce the prompt cache TTL from 1 hour to 5 minutes so cached prefixes expire before mid-conversation updates occur.
- **D.** Trigger on-demand compaction before every turn so the request prefix stays under the cache minimum threshold.

#### My Answer
**B** — Correct

#### Review
- **Why B wins:** Prompt caching is prefix-based (`tools` → `system` → `messages`), and preserved thinking enforces strict prefix integrity on prior thinking blocks. Mutating `system` or `tools` mid-conversation invalidates the entire cache prefix *and* trips preserved-thinking prefix checks (`400`). Appending mid-conversation updates and using deferred tool loading (`tool_search`) keeps the prefix immutable.
- **Why others fail:** Stripping thinking blocks (**A**) degrades multi-turn reasoning and still breaks the cache prefix; shortening TTL (**C**) makes caching worse; compacting every turn (**D**) destroys cache hits and adds latency/cost.

### Q3 — Domain 5: Evaluation Engineering & Quality Assurance

#### Question
Your team gates releases of a multi-turn billing agent with a CI eval suite that runs each task once (`pass@1`) and scores transcripts using an LLM-as-judge running the same model being evaluated. After a release passed CI at 94%, production incidents rose: the agent intermittently skips a mandatory refund-verification tool call on ~15% of runs, and the judge misses subtle arithmetic errors that human reviewers catch.

Which change best fixes **both** quality gaps?

- **A.** Raise the single-trial `pass@1` gate from 90% to 98% and add stricter wording to the judge's system prompt.
- **B.** Switch the CI gate to `pass@5` (passing if at least 1 of 5 trials succeeds) to absorb non-deterministic variance, and upgrade the judge to a larger model.
- **C.** Measure multi-trial consistency (`pass^k`) using deterministic code graders for mandatory tool calls and arithmetic checks, and calibrate a separate rubric-based judge against human-labeled transcripts before giving it merge-gating authority.
- **D.** Replace offline CI evals with 5% live-traffic A/B testing so non-deterministic failures are observed directly on real users.

#### My Answer
**C** — Correct

#### Review
- **Why C wins:** For customer-facing/financial agents where *every* run must follow policy, **`pass^k`** (all *k* trials succeed) exposes intermittent 15% failures that single-trial `pass@1` masks—whereas **`pass@5`** (**B**) goes the opposite direction (only requiring 1 of 5 to pass). Deterministic code graders should own verifiable facts like tool-call presence and arithmetic, while any LLM-as-judge must be calibrated against human labels before gating CI.
- **Why others fail:** Single-trial `pass@1` (**A**) still misses intermittent reliability drops; live-only A/B (**D**) shifts financial bugs onto real customers before catching them.

#### Question

Currently, they use 2% head-based sampling with full prompt and completion bodies attached to every span, and their cost dashboard sums `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` at the base input token rate.

Which combination of changes fixes **all** of these issues?

- **A.** Increase head-based sampling to 25% with client-side regex redaction of prompt bodies, and keep billing all three token counters at the base input rate to maintain a conservative cost ceiling.
- **B.** Disable prompt/completion content capture on OTel spans (recording only metadata, latencies, tool names, `stop_reason`, and token counts), switch to tail-based sampling that retains 100% of error/high-latency traces plus a small healthy baseline, and apply the separate cache-write and cache-read pricing multipliers rather than the base input rate.
- **C.** Query Anthropic's Compliance API to pull full prompt transcripts after ZDR requests finish, and exclude `cache_read_input_tokens` from cost dashboards because cache reads are free.
- **D.** Keep 2% head-based sampling to protect collector budgets, and rely exclusively on the daily Usage & Cost Analytics API to isolate individual tool-loop timeouts.

#### My Answer
**B** — Correct

#### Review
- **Why B wins:**

### Q5 — Domain 7: Runtime Guardrails, MCP Security & Threat Defense

#### Question
An enterprise Claude agent connects to a remote MCP server fronting an internal HR database and a Slack MCP server. For convenience, the HR MCP server accepts the caller's upstream bearer token and passes it straight through to downstream HR microservices, while relying on a system prompt rule: *"Never return salary data outside the requester's department."* During a red-team test, hidden instructions inside a shared Confluence page (read by the agent) cause it to query another department's salary records and post a summary to a public Slack channel.

Which architectural change **most directly** eliminates the root security vulnerabilities?

- **A.** Add an LLM output classifier to scan outbound Slack messages for currency symbols, and wrap Confluence content in stricter XML tags in the system prompt.
- **B.** Eliminate token passthrough by enforcing MCP OAuth 2.1 audience-scoped authorization with server-side row-level access checks tied to the verified caller identity, and place a deterministic `PreToolUse` / human-approval gate with channel allowlisting on the Slack tool.
- **C.** Run the agent inside a read-only Docker sandbox and lower the model's `effort` setting to `low` so it is less likely to follow multi-step injected instructions.
- **D.** Enable Zero Data Retention (ZDR) and Workload Identity Federation (WIF) on the Claude API connection so credentials cannot be exfiltrated through Slack.

#### My Answer
**B** — Correct

#### Review
- **Why B wins:** Token passthrough is explicitly forbidden by MCP security best practices (breaks audience validation and invites confused-deputy attacks). Enforcing OAuth 2.1 audience-scoped auth with **server-side** row-level authorization closes unauthorized reads—never trust a system prompt for access control. Adding a deterministic `PreToolUse` / human-approval gate + channel allowlisting on the Slack tool breaks the **Lethal Trifecta** *(untrusted input + private data + external communication)*.
- **Why others fail:** Probabilistic classifiers (**A**) and lowering `effort` (**C**) are bypassable; ZDR/WIF (**D**) protect API data/auth to Anthropic, not HR-to-Slack exfiltration.

#### Question

What is the best immediate mitigation **and** durable architectural fix?

- **A.** Strip only the `signature` field from historical `thinking` blocks on HTTP `400` retries so the API accepts the updated `system` prompt without resetting the session.
- **B.** Disable thinking for sessions that cross midnight UTC and instruct the model in the `system` prompt to write chain-of-thought inside `<reasoning>` XML tags instead.
- **C.** Switch from adaptive thinking to legacy extended thinking with a fixed `budget_tokens` of 1024, because legacy thinking does not enforce prefix integrity across turns.
- **D.** Recover in-flight sessions hitting the prefix-binding error by dropping historical `thinking` blocks on the recovery turn (or starting a clean thinking chain), and permanently move volatile fields like the current date out of the top-level `system` prompt into appended `user` messages so both preserved-thinking prefix checks and prompt caches remain valid across midnight.

#### My Answer
**D** — Correct

#### Review
- **Why D wins:** Preserved thinking cryptographically binds `thinking` blocks to the preceding prefix (`tools` + `system` + earlier messages). Moving volatile fields like timestamps out of `system` into appended `user` messages fixes both permanently.
- **Why others fail:** Stripping only `signature` (**A**) produces an invalid thinking block (still `400`); disabling thinking (**B**) degrades reasoning quality and still busts the cache; legacy thinking (**C**) does not solve the midnight cache-busting root cause.

### Q10 — Domain 5: LLM-as-Judge Bias, Calibration & Drift

#### Question
Your evaluation team uses a pairwise LLM-as-judge to compare candidate prompts against the production baseline across a 400-item golden set. To address position bias, they already randomize A/B order per item and see **84% raw agreement** with 3 human raters. However, auditing the disagreements shows the judge almost always picks whichever response is 2–3x longer—even when it includes an unsupported claim. Additionally, after upgrading the judge to a newer model snapshot last week, historical prompt scores jumped +11 points with zero changes to the prompts under test.

Which diagnosis and remediation plan is **most** accurate?

- **A.** 84% raw agreement is already strong enough for CI gating; constrain `max_tokens` on candidate prompts to match baseline length and freeze the golden set permanently so scores remain comparable.
- **B.** Replace the LLM-as-judge with exact-string matching against the golden set so model bias and judge drift are eliminated completely for open-ended generation tasks.
- **C.** The judge is suffering from **verbosity bias** and **judge drift** across model versions; pin the judge model version, evaluate position-swapped pairs (both A/B and B/A) with a length-agnostic decomposed rubric (scoring groundedness separately from completeness), measure chance-corrected inter-rater reliability (e.g., Cohen's kappa) against human labels, and re-calibrate/re-baseline whenever the judge model changes.
- **D.** Expand the golden set from 400 to 4,000 synthetic examples generated by the newer judge model so judge drift is absorbed into the evaluation distribution.

#### My Answer
**C** — Correct

#### Review
- **Why C wins:** Pairwise judges frequently exhibit **verbosity bias** (favoring longer responses even with unsupported claims), and upgrading the judge snapshot introduces **judge drift**. Pin the judge snapshot, run **swapped pairs (A/B and B/A)** with a **decomposed, length-agnostic rubric** (separating factual groundedness from completeness), measure chance-corrected agreement (**Cohen's kappa**, not just raw % agreement), and re-baseline whenever the judge model changes.
- **Why others fail:** Freezing a golden set forever (**A**) invites contamination/saturation; exact-string matching (**B**) breaks open-ended generation; generating synthetic evals with the judge (**D**) amplifies self-preference bias.

### Q12 — Domain 7: Runtime Guardrails, WIF & Irreversible Tool Actions *(Select TWO)*

#### Question
You are hardening a multi-tenant production Claude deployment on Kubernetes that runs autonomous financial-reconciliation workflows via the Claude API and internal MCP servers. A security audit flags two critical findings:
1. Pods authenticate to Anthropic using a shared, long-lived static `ANTHROPIC_API_KEY` mounted from a Kubernetes Secret across all tenants.
2. An agent with read access to uploaded customer invoice PDFs and write access to an outbound payment-webhook MCP tool has no deterministic runtime control preventing a poisoned PDF from triggering an unauthorized payout.

Which **TWO** controls directly remediate these audit findings? *(Select TWO.)*

- **A.** Rotate the shared static `ANTHROPIC_API_KEY` weekly via a CronJob and add a `PostToolUse` hook that logs outbound payment webhooks to Datadog for next-day review.
- **B.** Replace static API keys with **Workload Identity Federation (WIF)** using short-lived Kubernetes OIDC / SPIFFE credentials scoped to per-workload/tenant identities.
- **C.** Add a high-priority system prompt rule instructing Claude to refuse any payment instructions embedded in PDF invoices, and set `effort: "max"` so the model reasons more thoroughly before calling the payment tool.
- **D.** Enable 1-hour prompt caching and Zero Data Retention (ZDR) on the Claude API workspace so poisoned invoice PDFs are never retained by Anthropic.
- **E.** Enforce a deterministic runtime guardrail / `PreToolUse` approval gate outside the model (enforcing recipient allowlists, amount limits, and human/policy-engine approval before executing the irreversible payment-webhook MCP tool).

#### My Answer
**B, E** — Correct

#### Review
- **Why B wins:** Workload Identity Federation (WIF) eliminates shared static `ANTHROPIC_API_KEY` secrets by issuing short-lived, workload/tenant-scoped Kubernetes OIDC / SPIFFE credentials.
- **Why E wins:** Irreversible actions (payouts) exposed to untrusted input (uploaded PDFs) require **deterministic enforcement outside the model** (`PreToolUse` / policy engine / recipient allowlists / amount ceilings / human approval).
- **Why others fail:** Weekly rotation + `PostToolUse` logging (**A**) keeps a shared static secret and only detects payouts after money has left; prompt-only rules + `effort: "max"` (**C**) are probabilistic and bypassable; caching/ZDR (**D**) does not prevent unauthorized tool execution.
