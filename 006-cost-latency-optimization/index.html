Cost Architecture at Scale

Cost Modeling, Model Routing, and Multi-Model Cascades

KEY CONCEPT

Free Wins vs. Intelligence Tradeoffs

Live Read-Along (click any sentence to jump)
Before you downgrade a model or build a complex router, separate free wins from intelligence tradeoffs. Free wins like prompt caching, token hygiene, auditing stale prompts, and using the Batch API cut your bill without sacrificing quality. Only after you capture those free wins should you move along the frontier with effort sweeps, model routing, and multi-model architectures.

Cost optimization on the Claude Platform divides cleanly into two categories on the cost-to-intelligence frontier:

  • Free wins (move toward the frontier): Cut spend without touching quality—prompt caching, input/context token hygiene, auditing legacy prompts against the current model, and routing async work to the Batch API (50% off).
  • Intelligence tradeoffs (move along the frontier): Exchange cost for capability—model selection, effort sweeps, failure-triggered escalation, session/task budgets, and multi-model architectures.

Always exhaust free wins first—especially prompt caching, which is typically the single largest cost lever—before trading away model intelligence.

COST MODELING

Second, Claude Haiku five point five jumps five x in price across the whole request once total prompt length, including cached tokens, crosses one hundred thousand tokens.

EXAM TRAP

Compare Cost Per Completed Task—Not Cost Per Token

Live Read-Along (click any sentence to jump)
On the exam, always evaluate models on cost per completed task, never cost per token. A cheaper model that fails and retries often costs more than a stronger model that succeeds on the first try, and the hardest ten percent of your workload usually drives the bill. In the Agent SDK, remember that total cost USD is a client-side estimate, deduplicate parallel tool turns by message ID, and use model usage to capture subagent tokens.

Per-token comparisons mislead you because a stronger model often solves a task in fewer turns and retries, while a cheaper model's failed attempts still bill their tokens, the retry, and downstream failure costs. Furthermore, spend is heavily tail-skewed: in multi-step agent benchmarks, the hardest 10% of tasks routinely drive over 40% of total spend.

Telemetry caveat in Agent SDK: total_cost_usd and modelUsage are client-side estimates from a bundled price table—never use them to bill end users. When summing per-step usage in parallel tool turns, deduplicate assistant messages by message.id, read output totals from the final result message, and use modelUsage (not top-level usage) so subagent spend is included.

ARCHITECTURE PATTERN

Model Routing and Failure-Triggered Escalation

Live Read-Along (click any sentence to jump)
Before building a multi-model router, sweep the effort parameter on your primary model to establish a baseline curve. When your workload has a deterministic verifier like a test suite, a cascade that runs everything at low effort and re-runs only failures at high effort can cut cost by roughly forty percent at the same pass rate. Just remember the tradeoff: failed tasks incur two passes of wall-clock latency, and you still need to audit legacy prompts so newer models do not waste tokens on outdated instructions.
  • Start with an effort sweep before adding a second model: Tuning output_config.effort on a single model (e.g., Opus 5.5 or Sonnet 5.5) often outperforms multi-model complexity. Every candidate pairing must beat the single model's entire score-vs-spend effort curve.
  • Failure-triggered escalation (cascades): When outputs are deterministically checkable (unit tests, schema validators, verifiers), run every task at low effort first and re-run only failed tasks at high effort. In Anthropic's SWE-bench Pro measurements on Opus 5.5, this cascade achieved a ~97% pass rate for ~$0.17/task—about 40% cheaper than running everything at high ($0.29/task).
  • Tradeoff of cascades: You require a reliable failure verifier (a weak checker leaks bad outputs), and failed first-pass tasks pay two runs' worth of wall-clock latency.
  • Prompt audits on upgrades: Legacy instructions like "verify twice" or hand-rolled <scratchpad> tags make newer models waste tool rounds and output tokens; run /claude-api prompt-audit whenever upgrading models.
MULTI-MODEL PATTERNS

When a single model's effort curve is not enough, choose between two multi-model patterns. Use the Advisor pattern for serial work where a cheaper executor runs the loop and escalates hard decisions, but always verify the consult rate because an advisor that is never called only adds schema overhead. Use the Orchestrator pattern when work fans out cleanly or exceeds a single context window, such as pairing an Opus orchestrator with Sonnet subagents.

Cost Architecture at Scale

Prompt Caching Strategy, Batch Economics, and Budget Governance

KEY CONCEPT

Prompt Caching Mechanics, Lookback, and Breakpoints

Live Read-Along (click any sentence to jump)
Prompt caching is your highest-leverage cost control because multi-turn agent costs otherwise grow quadratically. Cache prefixes are evaluated in strict order: tools, then system, then messages. You can use top-level automatic caching or up to four explicit breakpoints, and reads walk backward up to twenty blocks to find a prior write. Watch the minimum cacheable threshold of five hundred twelve tokens on Claude five series models, and never put a breakpoint on a block that changes every request.

In a 40-turn agent loop without caching, turn 1 is resent 40 times—cost grows quadratically with turn count. Prompt caching hashes prefixes in strict hierarchical order: tools → system → messages. Well-tuned production agent loops read a median 84% of input tokens from cache (top 10% hit 94%+); anything below 80% signals a cache break.

  • Automatic vs. Explicit: Top-level cache_control: {"type": "ephemeral"} automatically places a breakpoint on the last cacheable block and advances it each turn. Explicit block-level breakpoints (up to 4 per request, zero extra fee per breakpoint) let you isolate sections that change at different rates.
  • 20-block lookback window: Writes happen only at marked breakpoints. On read, the API walks backward up to 20 blocks (consecutive tool_use or tool_result blocks count as one position) looking for a prior write. Placing a breakpoint on a varying suffix (e.g., a timestamp) causes 100% cache misses because lookback only finds prior writes, not arbitrary stable text.
  • Minimum cacheable length: 512 tokens on Claude 5.x models (Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5), 1,024 on Sonnet 5 / Opus 4.8, 2,048 on Opus 4.7, and 4,096 on Haiku 4.5 / Opus 4.6. Shorter prefixes silently skip caching without error.
CODE PATTERN

TTL Selection, Mixed TTLs, and Cache Keep-Alive

Live Read-Along (click any sentence to jump)
Cache lifetimes start when the request begins, not when streaming finishes, so a four-minute generation leaves only one minute on a five-minute cache. Use the five-minute default for rapid agent loops, and switch to the one-hour TTL when at least one in twenty gaps falls between five minutes and an hour. If you mix TTLs in one request, the one-hour breakpoint must come before any five-minute breakpoint. On Opus five point five and Fable five point two, you can also keep a five-minute cache warm with a zero-output max tokens request every four minutes.

Cache lifetimes run from the start of the request (generation time counts against the 5-minute TTL). Choose TTLs based on inter-turn pause distribution:

  • 5-minute default (1.25x write): Best when turns arrive seconds apart, or when ≥60% of pauses exceed 1 hour (both TTLs expire anyway).
  • 1-hour TTL (2x write, "ttl": "1h"): Wins when ≥1 in 20 gaps falls between 5 minutes and 1 hour and few exceed 1 hour.
  • Mixing TTLs rule: Longer TTL blocks must appear before shorter TTL blocks (1-hour before 5-minute).
  • Keep-alive alternative: On models with ultra-cheap cache reads (0.025x on Fable 5.2, 0.05x on Opus/Sonnet 5.5), re-sending the exact previous request with max_tokens: 0 (dropping stream) every 4 minutes refreshes the 5-minute cache for pennies—often beating 1-hour write pricing for short human pauses.
{
  "model": "claude-opus-5-5",
  "max_tokens": 4096,
  "system": [{
    "type": "text",
    "text": "<large stable system instructions>",
    "cache_control": {"type": "ephemeral", "ttl": "1h"}
  }],
  "messages": [
    {"role": "user", "content": [{"type": "text", "text": "...", "cache_control": {"type": "ephemeral"}}]}
  ]
}

BATCH ECONOMICS

Batch API vs. Real-Time Processing

Live Read-Along (click any sentence to jump)
For any workload where a human is not waiting synchronously, the Batch API is the second-largest free cost lever after prompt caching. It gives you a flat fifty percent discount on input, output, and even cached tokens in exchange for an asynchronous twenty-four-hour turnaround window. Use it for eval runs, backfills, and scheduled pipelines, and remember that batching stacks with prompt caching but cannot be combined with fast mode, message threads, or Managed Agents sessions.
  • 50% discount across all tokens: The Message Batches API cuts input, output, and cached token prices in half in exchange for asynchronous completion within a 24-hour window.
  • Best workloads: Offline evaluation suites, dataset backfills, document classification/extraction pipelines, and scheduled unattended agent sweeps where no human is waiting interactively.
  • Stacking rules: Batch discounts stack with prompt caching multipliers (e.g., shared system prompt across a batch) and long-context/data-residency modifiers.
  • Incompatibilities: Batch processing is not available with Fast Mode (speed: "fast"), Message Threads, or Claude Managed Agents sessions.

CODE PATTERN

Advisory Task Budgets for Graceful Self-Regulation

Live Read-Along (click any sentence to jump)
When you want an agent to wrap up gracefully instead of hitting a hard wall, use advisory task budgets under output config with the task budgets beta header. Claude sees a server-side countdown of tokens remaining for the full agentic turn, counting only new thinking, tool calls, tool results, and text—not resent history. If your application compacts history mid-loop, pass the remaining field forward so the countdown stays accurate.

Unlike hard dollar caps that cut off a session, Task Budgets (beta: task-budgets-2026-03-13) inject a server-side token countdown visible only to Claude so the model paces its thinking, tool calls, and tool results and summarizes findings gracefully before running out.

  • Counts only new tokens seen in the current agentic turn: Resent conversation history is not double-counted against the task budget.
  • Client-side compaction: If your harness summarizes/compacts history between requests, pass remaining so the countdown continues instead of resetting to total—but never decrement remaining manually when resending full uncompacted history.

    },

Latency Engineering

Latency Profiling, Streaming, and Tool-Call Parallelism

KEY CONCEPT

Distinguishing TTFT from OTPS and Total Latency

Live Read-Along (click any sentence to jump)
Never optimize latency blindly—first separate Time-To-First-Token from Output Tokens Per Second and total agent wall-clock time. Time-To-First-Token is dominated by prompt prefill, cache misses, payload tokenization, and up-front thinking, whereas total generation time depends on output length, model speed, and tool round-trips. Always lock in your quality baseline first, then apply one latency lever at a time against your evals.

Effective latency engineering starts by decomposing wall-clock wait time into distinct components—because levers that fix one metric often leave the other untouched:

  • Time-To-First-Token (TTFT): Time from request dispatch until the first response token arrives. Driven by network payload upload, request validation/tokenization, prompt prefill length, cache miss vs. hit, and up-front extended thinking.
  • Output Tokens Per Second (OTPS): Generation throughput once decoding starts. Driven by model size (Haiku 5.5 > Sonnet 5.5 > Opus 5.5) and Fast Mode (up to 2.5x OTPS).
  • Total / End-to-End Latency: TTFT + (output_tokens / OTPS) + tool_execution_time summed across every round-trip in an agent loop.

Golden rule: Engineer a prompt that meets your accuracy bar first, then apply latency optimizations one at a time while guarding quality with evals.

LATENCY LEVERS

Output Hygiene, Safe max_tokens Sizing, and Time Awareness

Live Read-Along (click any sentence to jump)
Watch out for a classic production mistake: shrinking max tokens to lower latency or cost. Because max tokens is invisible to Claude and includes thinking tokens, a tight cap silently truncates rare long turns with stop reason max tokens and wastes all the tokens you already paid for. Instead, keep max tokens generous—sixty-four thousand to one hundred twenty-eight thousand for agentic loops—prompt for concise sentence or paragraph structure, and use effort or elapsed-time signals to make the agent finish sooner.
  • Prompt for concise structure, not word counts: Ask for sentence or paragraph limits rather than exact word counts (LLMs count tokens, not words). Output tokens cost 5x input tokens and slow every turn, plus they get re-read on every future turn in an agent loop.
  • Do NOT shrink max_tokens to save cost or latency: max_tokens is invisible to the model and includes thinking tokens. Setting it too low (e.g., 16k on heavy agentic tasks) causes stop_reason: max_tokens cutoffs that discard paid work. Set max_tokens to 64,000–128,000 for agentic loops, stream the response, and use effort (which the model sees) to trim length.
  • Elapsed-time signaling: Telling an agent that time matters and injecting elapsed time on each request cut median task time by 7%–47% in Anthropic's benchmarks (for a modest score tradeoff—verify on your evals).
CODE PATTERN

SSE Streaming and Fine-Grained Tool Streaming

Live Read-Along (click any sentence to jump)
Standard server-sent event streaming improves perceived responsiveness for text and prevents HTTP timeouts on large generations, but by default the API buffers and validates tool call JSON before emitting it. For tools with large arguments like writing code files, set eager input streaming to true on the tool definition to stream raw JSON fragments immediately. Because server-side validation is bypassed, always guard your JSON parser against malformed or truncated payloads, and prefer the per-tool flag over the legacy beta header.

Enabling stream: true sends incremental Server-Sent Events (SSE) so users see text immediately and long generations avoid HTTP timeouts (required by SDKs for large max_tokens).

By default, however, the API buffers and validates each tool parameter's JSON before streaming it—creating multi-second stalls on large code or document tool arguments. Setting eager_input_streaming: true on a user-defined tool enables fine-grained tool streaming, delivering raw input_json_delta chunks immediately without server-side buffering.

tools = [{
    "name": "write_file",
    "description": "Write source code to disk",
    "eager_input_streaming": True,  # Replaces legacy beta header; safe with computer/browser use
    "input_schema": {"type": "object", "properties": {"path": {"type": "string"}, "content": {"type": "string"}}}
}]
with client.messages.stream(model="claude-opus-5-5", max_tokens=65536, tools=tools, messages=msgs) as stream:
    for event in stream:
        if event.type == "input_json":
            render_live_code_preview(event.partial_json)

Critical guard: Because server-side JSON validation is skipped, you must accumulate chunks, guard JSON.parse, and handle partial/invalid JSON or max_tokens cutoffs gracefully. Note: the legacy fine-grained-tool-streaming-2025-05-14 beta header is rejected when combined with computer use or browser use toolsets—use per-tool eager_input_streaming instead.

ARCHITECTURE PATTERN

Parallel Tool Execution & Message History Rules

Live Read-Along (click any sentence to jump)
Parallel tool execution collapses multiple sequential network round-trips into one. When Claude returns several independent read-only tool calls in a single turn, execute them concurrently with asyncio gather or Promise dot all, then return every tool result together in one user message before any text blocks. If a sequential call fails and you skip remaining calls, still return a tool result with is error true for each skipped ID, and remember that computer use and browser use batches must always run sequentially.
  • Collapse round-trips with concurrent dispatch: Claude emits multiple tool_use blocks in one assistant turn by default. Execute independent, read-only tools concurrently (asyncio.gather / Promise.all) so total tool wait equals the slowest single call rather than their sum.
  • Sequential exceptions: Run tools with shared mutable state sequentially. For computer use and browser use batch actions, you must run calls sequentially in order and stop at the first failure.
  • Strict history formatting to keep parallelism working: Return every tool_result together in a single user message, placed before any text blocks, matching each tool_use_id. If you skip a call after an earlier failure, still return a tool_result with is_error: true and an explanation.
  • Cache synergy: Consecutive tool_use or tool_result blocks count as a single position in the 20-block prompt cache lookback window.
LATENCY PATTERN

Cache Pre-Warming and Checkpointing for Low TTFT

Live Read-Along (click any sentence to jump)
Prompt caching is not just a cost lever—it is one of the strongest ways to slash Time-To-First-Token on long contexts. To remove the cold-start penalty on a user's first message, pre-warm the cache with max tokens set to zero and a placeholder user turn. Place an explicit cache control breakpoint on the shared static prefix—not automatic caching—match your production thinking and effort settings exactly, and wait for the warmup response to start before fanning out concurrent requests.

Prompt caching cuts TTFT dramatically on long contexts because cached prefixes skip full prefill computation. To eliminate the cold-start TTFT penalty on a user's very first turn, pre-warm the cache with max_tokens: 0 and a placeholder user message (e.g., "warmup"):

  • Use an explicit breakpoint, NOT automatic caching: Place cache_control on the last shared static block (tools or system prompt), never on the placeholder user message, or real traffic will miss the cache.
  • Match request parameters exactly: Send the exact same thinking configuration and output_config.effort as real traffic.
  • Concurrent fan-out rule: A cache entry becomes readable only after the first response starts—wait for the pre-warm response before fanning out parallel workers on the same prefix.

EFFORT TUNING

Calibrating output_config.effort and Adaptive Thinking

Live Read-Along (click any sentence to jump)
Output config dot effort is your primary dial for trading thinking depth against latency and cost. Remember the defaults: Opus five point five and Haiku five point five default to medium, while Sonnet five point five and Fable five point two default to high. Adaptive thinking is always on for Opus five point five and Fable five point two, so disabling thinking returns a four hundred error. Always adjust effort before trying prompt-based thinking steering, because prose instructions to skip thinking are unreliable on newer models.

output_config.effort is a behavioral signal (not a hard token budget) governing thinking frequency, thinking depth, and tool-call thoroughness across all output tokens:

Thinking controls: On Opus 5.5 and Fable 5.2, adaptive thinking is always on (sending thinking: {"type": "disabled"} returns a 400). Always lower effort before using prompt-based thinking steering—telling Sonnet 5.5, Haiku 5.5, or Fable 5.2 in prose to "answer directly" does not reliably stop thinking.

CACHE-SAFE TUNING

Per-Message Effort Without Breaking the Prompt Cache

Live Read-Along (click any sentence to jump)
A common exam trap is changing top-level effort mid-conversation to save latency on a simple follow-up, which actually blows up your prompt cache and costs twenty to forty times more. Instead, use the per-message effort beta header and append an empty-content system message carrying the new output config dot effort while leaving the top-level effort untouched. Keep that message pinned in place on subsequent turns so both the cache and preserved thinking blocks remain intact.

Changing top-level output_config.effort mid-conversation invalidates the prompt cache—costing 20x to 40x more on a 100k-token cached prefix. Use Per-Message Effort (beta: mid-conversation-output-config-2026-07-01) to shift effort dynamically while keeping the top-level value and cached prefix intact:

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    output_config={"effort": "high"},  # Top-level stays unchanged!
    messages=[
        {"role": "user", "content": "Design a zero-downtime Postgres migration plan."},
        {"role": "assistant", "content": "..."},
        {"role": "system", "content": [], "output_config": {"effort": "low"}},
        {"role": "user", "content": "Summarize step 2 in one sentence."}
    ],
    betas=["mid-conversation-output-config-2026-07-01"],
)
  • Activation rule: Placed directly after a user turn with new input, it takes effect immediately; placed elsewhere, it starts at the next user turn with new input (tool_result-only turns do not count).
  • Immutability: Never insert before already-sent turns or delete later, or preserved thinking blocks are invalidated. Not compatible with between_tools (Sonnet 5.5) or disabled thinking (Haiku 5.5).
EXAM TRAP

Fast Mode: OTPS Boost, Dedicated Rate Limits, and Fallback Traps

Live Read-Along (click any sentence to jump)
Fast mode gives up to two point five x higher output tokens per second on Opus five point five and Fable five point two at double the token price, with identical intelligence. Know three exam traps. First, fast mode speeds up output generation, not Time-To-First-Token. Second, it uses dedicated fast rate-limit headers. Third, falling back from fast mode to standard speed on a four-twenty-nine triggers a prompt cache miss because the two speeds do not share cached prefixes.

Setting speed: "fast" on supported models (Claude Opus 5.5, Claude Fable 5.2, Mythos 5.2) delivers up to 2.5x higher Output Tokens Per Second (OTPS) with zero change to intelligence, at 2x standard token pricing ($8/$40 MTok on Opus 5.5; $16/$80 MTok on Fable 5.2; stacks with caching and data residency).

  • Does NOT reduce TTFT: Fast Mode accelerates token generation throughput, not prompt prefill. Pair it with streaming to make the OTPS gain visible.
  • Separate rate limits: Fast Mode has dedicated limits reported in anthropic-fast-input-tokens-* and anthropic-fast-output-tokens-* headers; verify execution via response.usage.speed.
  • Fallback cache-miss trap: Catching a Fast Mode 429 and falling back to standard speed causes a prompt cache miss because fast and standard speeds do not share cached prefixes. (Set max_retries=0 on the fast call if you want immediate fallback.)
  • Cloud parity note: On Microsoft Foundry, Fast Mode uses dedicated model IDs ending in -fast (e.g., claude-opus-5-5-fast) and omits the speed parameter.
SERVER-SIDE STATE

Message Threads for Incremental History & Lower TTFT

Live Read-Along (click any sentence to jump)
Message threads cut Time-To-First-Token in long agent loops by storing the system prompt, tools, and conversation in encrypted server memory so each follow-up turn sends only the new messages and the previous message ID. Crucial distinction: message threads lower latency, not token cost, so you must still enable cache control on every request. Because threads are best-effort with a five-minute expiry and are not eligible for zero data retention, always keep your own history copy to replay on a four-oh-four.

In long agent loops, re-uploading, validating, and re-tokenizing a 150k-token history on every turn inflates TTFT. Message Threads (beta: message-threads-2026-08-12) hold the conversation server-side in encrypted memory so later turns send only new messages plus previous_message_id (omitting system and tools):

thread = client.beta.messages.thread(
    model="claude-opus-5-5",
    max_tokens=4096,
    cache_control={"type": "ephemeral"},  # STILL REQUIRED for cost savings!
    system="You are a production SRE assistant.",
)
resp1 = thread.send({"role": "user", "content": "Investigate spike in 503s."})
resp2 = thread.send({"role": "user", "content": "Check upstream latency too."})
  • Lowers TTFT, NOT token cost: Claude still reads the full conversation—you must keep cache_control enabled to get cache-read pricing.
  • Best-effort 5-minute TTL & 404 replay: Threads expire 5 minutes after the last request (deleted ≤1 hour). Your app remains the source of truth; on a 404, replay the full history in a new thread: {"type": "create"} request (handled automatically in-memory by the SDK thread helper).
  • Constraints: Not ZDR-eligible, does not support compaction or most context editing, and cannot be used with the Batch API.

CCDV-P Scenario Practice

Production Scenario Questions

Scenario 1: Diagnosing a Sudden Cache-Hit Collapse and Cost Spike

A production customer-support agent running on Claude Opus 5.5 averages 25 turns per ticket with a 40,000-token system prompt and 180 MCP tool definitions. After a release that added a live queue-position status line to the top of the system prompt and began toggling top-level output_config.effort between high and low on alternating turns, daily spend quadrupled and cache read ratio dropped from 91% to 8%. Which combination of changes best restores cost efficiency without degrading quality?

Answer: B — Putting a per-request status line at the front of the system prompt invalidates the entire system and messages cache on every turn, and changing top-level output_config.effort mid-conversation also invalidates the cached prefix (costing 20–40x more). Moving per-request text to the newest user turn, using cache-safe per-message effort, and deferring unused MCP tool schemas with defer_loading (loaded inline as tool_reference blocks without breaking the prefix) directly fixes all three root causes. Option A increases write costs (2x) without fixing prefix instability and risks max_tokens truncation. Option C is wrong because Message Threads lower TTFT, not token cost, and still require cache_control. Option D fails because Claude Opus 5.5 has always-on adaptive thinking (thinking: disabled returns a 400 error) and prose instructions do not reliably suppress thinking.

Scenario 2: Optimizing an Overnight Verification Fleet Under a Budget Cap

An engineering platform team runs an overnight automated code-remediation pipeline of 10,000 repository tasks on Claude Opus 5.5 at high effort using real-time Messages API calls, where every generated patch is verified by an automated unit-test suite. The pipeline has a 12-hour SLA and is currently over budget by 65%, with 22% of failed tasks ending with stop_reason: max_tokens at a 16,384-token cap. Which architecture change delivers the largest cost reduction while maintaining or improving the pass rate?

Answer: A — Because the pipeline is overnight (12-hour SLA fits the 24-hour Batch API window), moving to the Batch API immediately cuts all token costs (including cached tokens) by 50% with zero quality loss. Raising max_tokens from 16,384 to 64,000 eliminates wasted tokens from truncated turns (stop_reason: max_tokens), and because unit tests provide a deterministic failure verifier, running at low effort and re-running only failures at high effort cuts cost by another ~40% at the same or higher pass rate. Option B worsens truncations, doubles token costs via Fast Mode (which is also incompatible with Batch API), and adds advisor overhead without an effort baseline. Option C triggers Haiku 5.5's 5x long-context pricing cliff above 100k tokens and degrades coding pass rates. Option D retries truncations at the same cap, multiplying wasted spend.

Scenario 3: Fixing TTFT Spikes and UI Stalls in a Zero-Data-Retention Coding Agent

A financial-services firm operates an interactive coding agent on Claude Opus 5.5 under strict Zero Data Retention (ZDR) requirements. Users report two latency complaints: first, a 6-second delay before any text appears on the opening turn of a session (which loads a 50,000-token repository guide); second, the IDE freezes for 8–10 seconds whenever the agent invokes its write_file tool with large diffs. Enabling Fast Mode (speed: fast) sped up prose streaming after text started, but did not fix the initial 6-second delay or the write_file freezes, and occasional Fast Mode 429 fallbacks to standard speed caused sudden cost spikes. What should the team implement?

Answer: B — Fast Mode only accelerates Output Tokens Per Second (OTPS), not Time-To-First-Token (TTFT), and falling back from fast to standard speed causes a prompt cache miss because different speeds do not share cached prefixes. Pre-warming the static prefix with max_tokens: 0 and an explicit cache_control breakpoint eliminates the cold-start TTFT penalty while remaining ZDR-eligible (unlike Message Threads, which are NOT ZDR-eligible—eliminating Option A). Setting eager_input_streaming: true on write_file removes server-side JSON buffering so diffs stream immediately to the IDE (with guarded parsing for partial/invalid JSON). Option C fails because automatic caching on a warmup request keys the cache to the placeholder user message, and the legacy fine-grained beta header is rejected when combined with computer use toolsets. Option D worsens perceived latency and misuses the async Batch API.
