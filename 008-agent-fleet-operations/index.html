Parallel Agent Orchestration for Engineering Work

Parallel Fan-Out Patterns, Worktree Isolation & Fleet Failure Modes

KEY CONCEPT

Choosing the Right Parallel Orchestration Primitive

Live Read-Along (click any sentence to jump)
Claude Code offers five distinct ways to parallelize engineering work, and the exam tests whether you pick the right one for the job. The core decision comes down to who holds the plan and whether workers need to talk to each other. Use subagents for focused side tasks, agent view for independent background sessions, agent teams for collaborative peers, and dynamic workflows when a script should orchestrate dozens or hundreds of agents with cross-checking.

Claude Code provides five distinct ways to parallelize engineering work, differentiated by who holds the coordination plan, whether workers communicate directly, and whether execution runs locally or in the cloud. Picking the wrong primitive either floods a single context window or multiplies token spend unnecessarily.

Use Subagents for focused side tasks inside one conversation, Agent View (claude agents) to dispatch and monitor independent background sessions, Agent Teams (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1) when peer sessions must debate and share a task list, Dynamic Workflows when a repeatable script must fan out dozens to hundreds of agents and cross-check results, and /batch when splitting one large change into 5 to 30 worktree-isolated subagents.

CODE PATTERN

Git Worktree Isolation & Enforcement Boundaries

Live Read-Along (click any sentence to jump)
To prevent parallel agents from clobbering each other's edits, isolate them in git worktrees using the dash-dash-worktree flag or isolation colon worktree in subagent frontmatter. By default, worktrees branch from the remote default branch, called fresh, so set worktree baseRef to head when subagents must build on your unpushed local commits. Add a dot worktreeinclude file to copy gitignored secrets like dot env, and remember that Claude Code actively enforces four checks blocking edits and git redirects back into the main checkout.

Git worktrees give each parallel session its own working directory and branch while sharing the repository's .git history. Launch isolated sessions with claude --worktree <name> (under .claude/worktrees/<name>), permanently isolate a custom subagent with isolation: worktree in its frontmatter, and use .worktreeinclude (.gitignore syntax) to copy gitignored files like .env into fresh checkouts.

# .claude/agents/refactorer.md
---
name: refactorer
description: Applies mechanical refactors across isolated files
isolation: worktree
---

# settings.json — branch from local HEAD instead of default "fresh" remote
{
  "worktree": { "baseRef": "head" }
}

# .worktreeinclude — copy gitignored runtime files into every new worktree
.env
.env.local

While isolated, Claude Code enforces four runtime checks: blocking file edits targeting the main checkout, blocking shell commands whose working directory resolves to the main checkout, blocking git redirects (git -C, GIT_DIR, cd) into the main checkout, and blocking unparseable or dynamically computed command shapes.

ARCHITECTURE PATTERN

Task Decomposition, Merge Strategy & Quality Gates

Live Read-Along (click any sentence to jump)
Clean parallel execution depends on decomposition before you spawn a single agent. Partition file ownership across non-overlapping modules, especially in agent teams where teammates share a working tree, and stabilize shared interfaces first. Wire up TeammateIdle and TaskCompleted hooks that exit with code two to reject incomplete work automatically. Finally, understand worktree lifecycle locks: Claude Code locks active worktrees against cleanup sweeps and preserves any worktree with unpushed commits or dirty submodules.
  • Partition file ownership explicitly: Because Agent Teams do not auto-isolate teammates in worktrees, decompose tasks by non-overlapping modules (for example, frontend, backend, and tests) and freeze shared interface contracts before fan-out to prevent cascading merge conflicts.
  • Enforce quality gates with lifecycle hooks: Attach TeammateIdle, TaskCreated, and TaskCompleted hooks in team runs; exiting with code 2 blocks completion or idling and feeds actionable remediation instructions back to the teammate.
  • Manage worktree locks & cleanup: Claude Code holds a git worktree lock while an agent or background session runs so periodic sweeps (governed by cleanupPeriodDays) never delete active work. Worktrees with uncommitted changes, unpushed commits, or dirty submodules are preserved until explicitly cleaned up.
  • Prefer adversarial verification in large fan-outs: For 100+ file migrations or security sweeps, use a Dynamic Workflow that fans out per-file workers and runs a second verification phase to deduplicate and cross-check findings before presenting a single ranked result.
EXAM TRAP

Diagnosing Fleet-Level Failure Modes from Telemetry

Live Read-Along (click any sentence to jump)
Watch closely for four fleet failure modes on the exam. First, parallel sessions multiply token burn, and enabling ultracode lifts the concurrent subagent cap. Second, headless dash-p worktree runs leave locked worktrees behind until unlocked or swept. Third, inside a worktree, the CLAUDE PROJECT DIR variable still points to the main checkout while the hook's C W D field points to the worktree. Fourth, enabling experimental agent teams causes named subagents in interactive sessions to spawn as full teammates automatically.

When fleet telemetry shows spiking latency, 429 rate-limit cascades, or corrupted runs across parallel agents, check four common root causes:

  • Token multiplication & quota contention: Every parallel session, subagent, and teammate multiplies token consumption independently; /effort ultracode also bypasses the session's concurrent subagent limit and large-workflow warning.
  • Non-interactive worktree lock leaks: claude -p --worktree has no exit prompt, so it does not auto-clean its worktree and leaves the lock in place until a later sweep or manual git worktree unlock followed by git worktree remove.
  • Hook path drift inside worktrees: Inside a worktree, ${CLAUDE_PROJECT_DIR} still points to the main checkout root, while the hook input JSON's cwd follows the worktree. Scripts that read ${CLAUDE_PROJECT_DIR} inspect the wrong files.
  • Unintended team formation: When CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 is enabled in an interactive session, any subagent Claude names automatically launches as a full teammate (unless forked or passed isolation), inflating token spend.
Verification and AI Code Review Operations

AI Code Review Pipelines, Shadow Calibration & Human Oversight

KEY CONCEPT

Closing the Verification Gap When Generation Outpaces Review

Live Read-Along (click any sentence to jump)
When coding agents accelerate generation, human code review quickly becomes your tightest bottleneck. Managed Code Review tackles this with a four-stage pipeline: parallel agents find issues, a separate verification stage filters out false positives, a ranking stage deduplicates by severity, and the final stage posts inline comments plus a check run. Crucially, the service has read-only access, never executes your code, and never approves or blocks a pull request on its own.

When agent fleets multiply pull request volume, human code review becomes the delivery bottleneck—and rubber-stamping AI-generated diffs introduces silent regressions. Anthropic's managed Code Review service addresses this with a four-stage pipeline running on Anthropic infrastructure: (1) Find (parallel agents inspect the diff and surrounding code), (2) Verify (a dedicated verification step checks candidate findings against the code to drop false positives), (3) Rank (remaining findings are deduplicated and ordered by severity), and (4) Post (inline comments, a summary, and a Claude Code Review check run).

By design, Code Review focuses on production correctness rather than style nits, has read-only repository access without building or executing code, and never approves or blocks a pull request—keeping merge authority with human engineers.

CONFIGURATION

Calibrating Findings with REVIEW.md & Branch Protection

Live Read-Along (click any sentence to jump)
Review dot M D is your primary calibration lever for managed Code Review. Use it to define what counts as an Important finding versus a Nit, cap nit comments so developers don't suffer alert fatigue, skip generated files or checks CI already runs, and demand file-and-line citations to cut false positives. For security, Code Review only reads Review dot M D from your protected base or default branch, never from the pull request itself, preventing a PR from disabling its own checks.

REVIEW.md tailors the managed Code Review service without polluting general coding instructions in CLAUDE.md. Use it to redefine severity thresholds, cap nit volume, exclude generated or CI-checked paths, add mandatory domain invariants, and require explicit file:line citations to suppress speculative false positives. You can modularize up to 8 root-level includes (@review-security.md) or project skill files (@.claude/skills/<folder>/SKILL.md, max 30 KB each, 150 KB combined).

# REVIEW.md (committed to protected default branch)
## What Important means here
Reserve Important for data leaks, unscoped tenant queries, or non-backward-compatible migrations.
Style and naming suggestions are Nit at most.

## Cap the nits
Report at most five Nits per review.

## Do not report
- Lint, formatting, or type errors already enforced by CI
- Generated code under src/gen/ and *.lock files

## Evidence requirement
Behavior claims must cite an exact file:line in the source, not an inference from naming.

Security rule: Code Review reads REVIEW.md only from the protected base or default branch—never from the PR's own changes—so an untrusted PR cannot weaken its own review rules.

ROLLOUT PATTERN

Shadow Mode, Human Calibration & Oversight Design

Live Read-Along (click any sentence to jump)
Never turn an uncalibrated AI reviewer into a hard merge gate on day one. Introduce it in shadow or advisory mode first, measuring precision, false-positive rate, and escaped bugs against your human reviewers. Iterate on Review dot M D and per-repo review levels until engineers trust the signal. Always separate the generating agent from the verifying agent, and design risk-tiered human oversight so senior engineers focus on architecture and security-critical paths while AI handles mechanical correctness.
  • Introduce in shadow / advisory mode first: Start with non-blocking reviews (Code Review's check run intentionally never concludes as a failure) on a pilot set of repositories so you collect signal without stalling merge velocity.
  • Calibrate against human review before gating: Track precision (actionable findings / total posted), false-positive rate, developer dismissal rate, and escaped defects against human reviewers. Tune REVIEW.md and review levels (Quick for routine repos, Deep for critical services) until noise is low enough that developers trust every Important flag.
  • Separate generation from verification: Never rely on the same agent context that wrote a change to self-certify it. Pair agentic authoring with an independent verifier pass—such as Code Review's Verify stage, Ultrareview's cloud reproduction fleet, or deterministic CI tests and static analysis.
  • Design risk-tiered human oversight: Require human sign-off on high-blast-radius paths (auth, billing, migrations, IAM) using subdirectory REVIEW.md files and GitHub CODEOWNERS, while letting AI review absorb mechanical correctness checks so human reviewers focus on architecture and intent.
EXAM TRAP

Subtle Code Review & Ultrareview Operational Gotchas

Live Read-Along (click any sentence to jump)
Three specific traps show up frequently in review architecture questions. First, if your default branch is unprotected, managed Code Review refuses to honor Review dot M D exclusions, nit caps, and subdirectory files. Second, local slash code-review reads Claude dot M D but completely ignores Review dot M D. Third, never script ultrareview with claude dash-p; it exits before findings return. Use the blocking claude ultrareview subcommand with dash-dash-trust-workspace instead.
  • Unprotected default branch breaks exclusions: If your default branch lacks branch protection (or a ruleset requiring PR approval that dismisses stale approvals), Code Review ignores REVIEW.md severity downgrades, path exclusions, nit caps, @ includes, and subdirectory REVIEW.md files (and subdirectory files under names like tests, generated, or vendor are always skipped).
  • Local /code-review ignores REVIEW.md: Put rules that must apply in both local sessions and PR reviews in CLAUDE.md; keep PR-specific calibration in REVIEW.md.
  • Scripting Ultrareview in CI: Running claude -p '/code-review ultra' exits immediately without waiting for findings and never posts. In scripts or CI, use the blocking claude ultrareview <PR> --trust-workspace --json (or --post) subcommand, which writes progress to stderr and parseable findings to stdout.
  • A clean AI review is not proof of safety: Zero findings never guarantees bug-free or secure code; always pair AI review with deterministic build, test, and security gates in CI.
Unattended and Event-Driven Agent Operations

Goal Loops, Scheduled Routines, Channels & CI/CD Incident Responders

KEY CONCEPT

Selecting the Right Unattended Execution Pattern

Live Read-Along (click any sentence to jump)
Unattended agent operations fall into three buckets: condition-driven loops that work until a goal is verified, time-driven schedules that run on a cadence, and event-driven responders that wake up on alerts, webhooks, or pull requests. Matching the right primitive to durability and environment needs is essential. Never run mission-critical nightly triage in a laptop-bound slash loop, and prefer push-based event triggers over wasteful polling whenever your pipeline supports them.

Unattended software delivery spans three distinct triggers: condition-driven work that iterates until a verifiable end state holds (/goal), time-driven work that runs on a cadence (session-scoped /loop or durable cloud scheduled tasks / routines), and event-driven responders that react immediately to webhooks, CI failures, alerts, or chat messages (Channels, API-triggered routines, GitHub Actions, and GitLab CI/CD).

Staff engineers match the execution surface to durability, local-state needs, and compliance boundaries: never rely on a laptop-bound /loop for nightly production triage, and never poll on a timer when an event-driven webhook or Channel can push failures directly into a responder.

DESIGN PATTERN

Goal-Driven Execution, Checkpointing & Failure Handling

Live Read-Along (click any sentence to jump)
Slash goal works by attaching a session-scoped prompt-based Stop hook evaluated by a fresh small fast model. Because that evaluator cannot run commands itself, write conditions that Claude proves directly in the transcript, paired with a turn cap and auto permission mode. Claude Code distinguishes error classes automatically: it retries transient network errors up to three times, pauses on rate limits, clears the goal on unrecoverable errors like auth failures, and uses exponential backoff check-ins when background tasks run long.
  • Fresh-evaluator verification: /goal wraps a session-scoped prompt-based Stop hook evaluated by the small fast model (ANTHROPIC_DEFAULT_HAIKU_MODEL). After each turn, the evaluator inspects only what Claude surfaced in the transcript and returns Met, Not yet met (with next-turn guidance), or Impossible (auto-clearing the goal).
  • Write observable end states & bounds: Always specify a concrete proof (for example, npm test exits 0 and git status is clean), negative constraints (no unrelated test files modified), and a turn or time cap (or stop after 20 turns). Pair with auto mode so tool prompts don't stall the loop.
  • Distinguish transient vs. unrecoverable errors: Claude Code automatically retries transient failures (overloaded server, dropped connection, up to 3 attempts), pauses on rate/usage limits, and clears the goal on unrecoverable errors requiring human intervention (auth failure, disk full, exhausted credits, unrecoverable context overflow).
  • Background check-ins & stall protection: While background work runs, evaluation is deferred; after 30 minutes Claude Code issues check-ins with exponential backoff (30m → 1h → 2h, capped at 3 idle check-ins). If Claude takes consecutive turns with no tool calls, the loop halts and returns control to the operator.
CODE PATTERN

Headless CI/CD Responders, --bare Mode & OIDC Federation

Live Read-Along (click any sentence to jump)
When running Claude Code in CI or incident response scripts, pass dash-dash-bare with dash-p to skip host auto-discovery and guarantee deterministic, fast starts. Pair it with explicit allowedTools, a JSON schema for machine-parseable output, and max-budget-usd to cap runaway spend. In GitHub Actions, replace static API keys with OIDC workload identity federation using id-token write, and rely on the action's built-in write-access and human-actor gates to prevent unauthorized triggers and infinite bot loops.

For scripted pipelines and CI/CD incident first response, run claude --bare -p so startup skips auto-discovery of host hooks, plugins, auto memory, and CLAUDE.md, giving deterministic execution. Combine --output-format json, --json-schema, --allowedTools, and --max-budget-usd to bound spend and parse results reliably.

# Deterministic headless CI triage with schema validation and budget cap
cat alert-payload.json | claude --bare -p \
  "Diagnose the root cause and propose a minimal fix." \
  --allowedTools "Read,Grep,Glob" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"root_cause":{"type":"string"},"severity":{"enum":["sev1","sev2","sev3"]}},"required":["root_cause","severity"]}' \
  --max-budget-usd 2.00

In GitHub Actions (anthropics/claude-code-action@v1), replace static API keys with OIDC workload identity federation (id-token: write + anthropic_federation_rule_id). The action enforces two built-in safety gates before starting: the triggering user must have write access and must be a human actor (blocking bots unless explicitly listed in allowed_bots to prevent infinite bot loops).

SECURITY & ESCALATION

Untrusted Event Payloads, Notification & Escalation Design

Live Read-Along (click any sentence to jump)
Unattended responders are prime targets for prompt injection and runaway side effects. Cloud routines automatically wrap incoming API fire text inside an untrusted routine-fire-payload tag so a leaked trigger token cannot hijack instructions. For CI incident responders, always escalate by opening a draft pull request and paging on-call rather than auto-merging fixes. And if you enable channels with permission relay, guard your sender allowlist tightly because allowlisted senders can approve tool execution remotely.
  • Prompt-injection defense on API triggers: When an alerting system POSTs freeform text to a cloud routine's /fire endpoint, Claude Code wraps it in a <routine-fire-payload> block labeled as untrusted data. The routine's saved prompt must explicitly opt in to reading that block, preventing a leaked bearer token from injecting arbitrary instructions.
  • Graceful termination & checkpointing: Stopping a claude -p job with SIGTERM exits with code 143, terminates running Bash process trees, and runs SessionEnd hooks without starting new tool calls; set CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1 if your supervisor resumes interrupted runs.
  • Escalation over auto-merge: For incident first response (such as Sentry alert triage), design the responder to correlate stack traces with recent commits, open a draft PR with a proposed fix, and notify the on-call engineer with links—keeping human approval in the merge path.
  • Channel security: For --channels, always lock sender allowlists after pairing; any allowlisted sender can also approve or deny tool calls if the channel declares the permission relay capability.
Organization-Wide Coding Agent Configuration

Managed Settings, MCP Governance, Gateway Routing & Shared Artifact Bar

KEY CONCEPT

Managed Settings Precedence, Composition & Fail-Closed Delivery

Live Read-Along (click any sentence to jump)
Organization-wide governance starts with the managed settings hierarchy. Claude Code checks remote server-managed settings first, then MDM or OS-level policies like macOS plists and Windows HKLM, then system managed-settings dot json files and drop-in directories, and finally HKCU only if no admin source exists. By default, the first source with a policy key wins, though critical security locks and environment variables read across admin sources. Set managedSourcesBehavior to merge to compose sources, and enable forceRemoteSettingsRefresh for fail-closed startup.

Enterprise coding-agent governance rests on managed settings, which outrank user, project, local, and --settings files. Claude Code evaluates four managed sources in priority order: (1) Remote settings (claude.ai server-managed settings or a self-hosted Claude apps gateway, polled hourly), (2) MDM / OS policy (macOS com.anthropic.claudecode plist or Windows HKLM\SOFTWARE\Policies\ClaudeCode), (3) File-based (managed-settings.json plus alphabetically merged drop-ins in managed-settings.d/*.json), and (4) Windows HKCU (user-writable fallback only when no admin source exists).

By default, managedSourcesBehavior is "first-wins"—the highest-ranked source with a policy key wins (except cross-source locks like allowManagedMcpServersOnly, deniedMcpServers, sandbox locks, and per-key env). Set managedSourcesBehavior: "merge" in the top source to compose all admin sources, and set forceRemoteSettingsRefresh: true to enforce fail-closed startup if remote policy cannot be fetched. Verify active sources on any machine via /status or claude doctor.

CONFIGURATION

MCP Allowlists, Exclusive Control & Plugin Marketplace Lockdown

Live Read-Along (click any sentence to jump)
For MCP governance, match the mechanism to your threat model. Deploy a system managed-mcp dot json file for exclusive control, or an empty map to disable MCP altogether. Use managedMcpServers in managed settings to push HTTPS remote servers without blocking user servers, or enforce an approved catalog with allowedMcpServers plus allowManagedMcpServersOnly set to true. Lock down plugins with strictKnownMarketplaces and disableSideloadFlags, and pre-seed air-gapped CI images using CLAUDE CODE PLUGIN SEED DIR.

Choose the MCP control pattern that matches your security posture: exclusive control via an OS-deployed managed-mcp.json (use an empty "mcpServers": {} map to disable MCP entirely), additive org servers via managedMcpServers in managed settings (HTTPS-only http/sse, no command or ${VAR}), or policy-based filtering with allowedMcpServers + allowManagedMcpServersOnly: true + deniedMcpServers (the denylist applies to every server, including managed ones).

// managed-settings.json — enterprise lockdown baseline
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./secrets/**)"],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowManagedHooksOnly": true,
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [{ "serverName": "github" }, { "serverName": "sentry" }],
  "deniedMcpServers": [{ "serverName": "unvetted-shell-mcp" }],
  "strictKnownMarketplaces": [{ "source": "github", "repo": "acme-org/approved-plugins" }],
  "disableSideloadFlags": true
}

Pair strictKnownMarketplaces with disableSideloadFlags: true (blocking --plugin-dir, --agents, and --mcp-config) and strictPluginOnlyCustomization. For air-gapped containers and CI runners, pre-populate a read-only plugin directory at build time and point CLAUDE_CODE_PLUGIN_SEED_DIR to it.

ARCHITECTURE PATTERN

Gateway Routing & Enterprise OpenTelemetry Observability

Live Read-Along (click any sentence to jump)
A self-hosted Claude apps gateway centralizes authentication, upstream routing, and observability inside your private network. Developers sign in with corporate OIDC single sign-on rather than holding cloud keys, while the gateway enforces per-group model allowlists, pushes managed settings, handles failover across Bedrock, Google Cloud, or Foundry, and exports OpenTelemetry metrics to your stack. Notice the security design: Claude Code rejects public gateway IPs at login, and OTLP exporter variables and credential helpers are always applied as an atomic unit.
  • Self-hosted Claude apps gateway (claude gateway): Built directly into the Linux claude binary, it sits between developer machines and Amazon Bedrock, Claude Platform on AWS, Google Cloud, Microsoft Foundry, or the Anthropic API. Developers authenticate via corporate OIDC SSO (short-lived JWTs backed by PostgreSQL; instant offboarding via IdP), while the gateway holds upstream cloud credentials and performs multi-upstream failover.
  • Private-network security guard: Claude Code's /login only connects to a gateway whose hostname resolves to private IP ranges (RFC 1918, CGNAT, ULA, loopback) because a trusted gateway can push managed settings and hooks to developer machines.
  • Per-group RBAC & OTLP telemetry: The gateway maps IdP groups to server-enforced model allowlists, managed settings policies, and upstreams, and emits OpenTelemetry (OTLP) metrics (tokens, model, user identity, latency) plus opt-in logs and traces directly to your observability stack—with zero data plane traffic sent to Anthropic when using cloud upstreams.
  • Telemetry unit atomicity: Across managed settings sources, OTEL_EXPORTER_OTLP_*, OTEL_LOG_*, and otelHeadersHelper are evaluated as an atomic unit from the highest source defining any of them, preventing an exporter endpoint from one tier from pairing with credentials from another.

Quality & Safety Bar for Sharing Prompts, Skills & MCP Servers

Live Read-Along (click any sentence to jump)
Sharing Skills, prompts, and MCP servers across teams requires a real software release bar. Enforce separation of duties and run a security checklist covering bundled scripts, prompt manipulation, network calls, and secrets. Turn on automated Skill scanning where available, but remember it does not cover Skills API uploads or ZDR and HIPAA orgs. Gate every release with evaluations for triggering accuracy, coexistence, and multi-model quality, keep bundles under the twenty-Skill API recall limit, and always pin exact versions in production.
  • Security review & separation of duties: Treat shared Skills, prompts, and MCP servers like production software. Audit all bundled scripts (*.py, *.sh, *.js) in a sandbox, check for instruction manipulation, network exfiltration patterns, broad filesystem globs, and hardcoded credentials—and ensure authors never approve their own submissions.
  • Automated scanning + manual review: Enable Skill and plugin security scanning on Claude Enterprise (blocks failed or pending scans in claude.ai/Cowork), but never rely on it alone: scanning does not cover Skills uploaded via the Skills API (/v1/skills) or orgs using ZDR, HIPAA, or CMEK.
  • Pre-deployment evaluation gates: Require 3–5 representative test queries per Skill (positive triggers, negative non-triggers, and ambiguous edge cases) tested across all deployed models (Haiku, Sonnet, Opus) for triggering accuracy, isolation, coexistence (no trigger stealing), and output quality.
  • Recall limits & version pinning: Keep active role-based bundles focused (the Skills API enforces a maximum of 20 Skills per request, and excess metadata degrades recall). Store Skills in Git with signed commits, compute integrity checksums, and pin explicit versions in production so an upstream edit never silently mutates live agents.

Enterprise Rollout Traps to Watch on the Exam

Live Read-Along (click any sentence to jump)
Keep four enterprise gotchas front of mind on exam day. First, managed-mcp dot json is a local OS file and cannot be pushed through server-managed settings. Second, Claude apps gateway requires browser SSO with no service-token flow, so CI pipelines must connect directly to your provider via OIDC. Third, Anthropic-hosted cloud sessions cannot see laptop MDM policies, so govern them via server-managed settings. Fourth, custom Skills do not auto-sync across API, web, and Claude Code, so treat Git as your single source of truth.
  • managed-mcp.json vs. server-managed settings: You cannot distribute managed-mcp.json through claude.ai server-managed settings; it must be placed at the OS system path via MDM or config management. Use server-managed allowedMcpServers, deniedMcpServers, or managedMcpServers when you lack MDM.
  • CI pipelines cannot use claude gateway SSO: Because Claude apps gateway uses an interactive browser SSO flow with no service-token flow, headless CI/CD pipelines must authenticate directly to your cloud provider (for example via OIDC federation) rather than through the gateway.
  • Cloud sessions ignore device MDM policies: Sessions running on Anthropic-hosted cloud infrastructure never read a laptop's plist, registry, or managed-settings.json—you must configure server-managed settings to govern cloud sessions.
  • Custom Skills do not sync across surfaces: Skills uploaded to the Claude API are not automatically available in claude.ai or Claude Code. Maintain Git as the single source of truth and automate synchronized deployment per surface.

Production Scenario Questions

Scenario 1: Parallel Migration Fleet Conflicts & Hook Failures

A platform team is migrating 400 legacy JavaScript React components to TypeScript using Claude Code. They enabled `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` and asked a single lead session to spawn 12 teammates to edit components in parallel. Within 10 minutes, fleet telemetry shows severe 429 rate-limit spikes, git merge conflicts across shared utility files, and a pre-commit style hook using `${CLAUDE_PROJECT_DIR}/.claude/hooks/lint.sh` checking stale files even when they tested a `--worktree` session. Which architectural redesign best resolves these failure modes?

Answer: B — B directly solves every failure mode: Agent Teams do not auto-isolate teammates in worktrees and are meant for a handful of collaborative peers, whereas a Dynamic Workflow (or `/batch`) is purpose-built to orchestrate dozens-to-hundreds of isolated per-file workers with a repeatable verification pass and bounded concurrency. Updating the hook to read `cwd` from its JSON input fixes the documented worktree behavior where `${CLAUDE_PROJECT_DIR}` stays pinned to the main checkout. A worsens file conflicts and rate limits. C is wrong because `/effort ultracode` actually lifts the concurrent subagent cap (worsening 429s) and `-p --worktree` leaves locked worktrees behind without cleanup. D serializes a 400-file migration into a fragile 7-hour local loop.

Scenario 2: Calibrating AI Code Review Without Stalling Delivery

After adopting coding agents across 60 repositories, pull request volume tripled and human reviewers are overwhelmed. Leadership wants to immediately make AI Code Review a required blocking check on every PR. During a one-week trial, developers complain that managed Code Review is posting 15+ formatting nits per PR, ignoring a new `REVIEW.md` exclusion rule committed to the unprotected `main` branch, and missing repository rules when developers run `/code-review` locally before pushing. What should the Staff Engineer recommend?

Answer: B — B reflects best-practice verification operations and exact product mechanics: introduce AI review in shadow/advisory mode and calibrate precision/false-positive rates against human reviewers before gating; protect the default branch because managed Code Review ignores `REVIEW.md` nit caps, severity downgrades, and path exclusions on unprotected branches; and put rules needed locally in `CLAUDE.md` because local `/code-review` does not read `REVIEW.md`. A fails because Code Review never concludes as a failure and never reads `REVIEW.md` from the PR branch itself. C fails because `claude -p '/code-review ultra'` exits immediately without waiting for findings (CI must use `claude ultrareview`). D violates generator/verifier separation and removes essential human oversight.

Scenario 3: Enterprise Gateway, MCP Lockdown & Unattended CI Triage

A regulated enterprise using Amazon Bedrock wants to deploy Claude Code to 800 engineers and also run an automated GitHub Actions workflow that triages failed production deploys. Security requires: (1) developers authenticate via Okta OIDC with no AWS keys on laptops, (2) OTLP usage metrics go only to the company's internal collector, (3) developers can only connect to two vetted MCP servers, and (4) GitHub Actions runs without static API keys. Which architecture meets all four requirements?

Answer: A — A satisfies every requirement and respects every architectural constraint: `claude gateway` on a private network provides Okta OIDC SSO, holds Bedrock credentials server-side, and exports OTLP telemetry internally; `allowedMcpServers` + `allowManagedMcpServersOnly: true` (or OS-deployed `managed-mcp.json`) restricts developers to the two vetted MCP servers; and because `claude gateway` uses interactive browser SSO with no service-token flow, GitHub Actions authenticates directly to Bedrock via OIDC. B fails on three counts: `managed-mcp.json` cannot be delivered via server-managed settings, `/login` rejects public gateway IPs, and the gateway has no service-token flow. C violates the no-static-keys requirement and uses a denylist instead of an allowlist. D fails because CI cannot use gateway browser SSO, `forceLoginOrgUUID` must not be placed in a gateway's `managed` block, and `managedMcpServers` is additive rather than exclusive.
