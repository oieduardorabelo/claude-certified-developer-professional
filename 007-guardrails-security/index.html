Runtime Guardrail Systems

Layered Runtime Guardrails, Filtering, and Hooks

KEY CONCEPT

Risk-Profiled Layered Guardrails and Harmlessness Screens

Live Read-Along (click any sentence to jump)
Production guardrails should match your agent's actual risk profile through layered defenses, not a single prompt instruction. Start with deterministic input validation and PII redaction, then add a fast harmlessness screen using Claude Haiku five point five with structured JSON output config. One critical detail: if the screening call itself returns stop reason refusal, treat that as a harmful verdict and trigger your safety fallback rather than failing open.

Production guardrail architectures scale to the agent's risk profile rather than relying on a single filter. A typical defense-in-depth stack layers deterministic input validation and PII redactors in front of lightweight harmlessness screens—for example, running Claude Haiku 5.5 with output_config JSON schema constraints to return a structured boolean verdict (is_harmful or injection_suspected) before the main model acts.

Because classifier models run Anthropic's own safety classifiers, a screening call itself can return stop_reason: "refusal" with no parsed verdict. Always treat a refusal from a screening model as a harmful verdict and route to a safe fallback response.

ARCHITECTURE PATTERN

Three Tiers of Hook-Based Policy Enforcement

Live Read-Along (click any sentence to jump)
You have three distinct hook layers across the Claude ecosystem. Claude Code hooks enforce local workspace policies like PreToolUse and ConfigChange. Agent SDK hooks run in-process callbacks to deny or modify tool inputs deterministically. Finally, Platform Inference Hooks govern every Claude Enterprise surface inline before inference runs, supporting shadow mode, rollout percentages, and circuit breakers—though they only allow or deny, never rewrite prompts or inspect raw image bytes.

CODE PATTERN

Deterministic Enforcement for Irreversible Actions in Agent SDK

Live Read-Along (click any sentence to jump)
For irreversible actions like writing secrets or executing destructive commands, enforce deterministic PreToolUse hooks in the Agent SDK that return permission decision deny. Notice the classic production trap here: matching only Write and Edit tools leaves a gap if the agent also has Bash access. Always pair tool-level hooks with OS-level sandbox restrictions so the agent cannot route around your matcher through a shell command.
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

async def block_sensitive_writes(input_data, tool_use_id, context):
    file_path = input_data["tool_input"].get("file_path", "")
    if file_path.split("/")[-1].lower() == ".env":
        return {
            "hookSpecificOutput": {
                "hookEventName": input_data["hook_event_name"],
                "permissionDecision": "deny",
                "permissionDecisionReason": "Modifying .env files is prohibited."
            }
        }
    return {}  # Defer to normal permission evaluation

options = ClaudeAgentOptions(
    hooks={
        "PreToolUse": [HookMatcher(matcher="Write|Edit", hooks=[block_sensitive_writes])]
    }
)

Critical coverage gap: A Write|Edit matcher only intercepts those specific tools. If the agent has Bash enabled, it can still overwrite .env via shell redirection unless you also enforce OS-level sandbox filesystem rules or hook Bash.

EXAM TRAP

Refusal Handling, FP/FN Tuning, and Denied-Conversation Loops

Live Read-Along (click any sentence to jump)
Watch out for three exam traps around runtime guardrails. First, never feed stop reason refusal into a generic retry loop—treat it as a safety class with a dedicated fallback. Second, use shadow mode and staged rollout percentages to tune false positives against false negatives before enforcing hard blocks. Third, remember that Inference Hooks inspect the full transcript, so after a denial the user must edit or rewind the offending turn or every follow-up message will be blocked too.
  • Never blindly retry stop_reason: "refusal": Safety refusals are a distinct failure class from 429 rate limits or max_tokens truncations. Retrying a refusal wastes tokens and repeats the block; route to a safety-handling path and throttle repeat offenders.
  • Calibrate false positives vs. false negatives: Roll out inline guardrails (such as Inference Hooks) in shadow mode and incremental rollout percentages first to measure false-positive friction against false-negative leakage before switching to fail-closed blocking.
  • Inference Hooks transcript loop: Because each Inference Hook request sends the entire conversation transcript, a denied message stays in history and causes every subsequent turn to fail until the user removes it (edit the message in claude.ai, run /rewind or /clear in Claude Code, or @Claude !restart in Slack).
ARCHITECTURE PATTERN

Approval Gates and Permission Policies

Live Read-Along (click any sentence to jump)
Approval gates let you keep humans in the loop for high-impact actions without causing prompt fatigue on safe reads. In Managed Agents, server-executed tools support always allow, always ask, and auto classifier policies, with MCP toolsets safely defaulting to always ask. In Claude Code, Auto mode uses a separate classifier while still respecting explicit deny rules, and critical path removals always force approval even when an allow rule matches.
  • Managed Agents permission policies: Apply to server-executed toolsets (prebuilt agent_toolset_20260401 defaults to always_allow; MCP toolsets default to always_ask). Choose always_allow, always_ask (pauses session for human confirmation), or auto (server-side classifier allows, denies, or escalates to confirmation). Custom tools run in your own application and enforce their own gates.
  • Claude Code permission modes: Auto mode routes actions through a separate classifier model while still honoring explicit ask and deny rules; Manual mode starts read-only and fails closed on unmatched commands; Accept Edits mode auto-approves in-directory edits and basic filesystem commands while still prompting on out-of-scope or network commands.
  • Critical-path removal gate: In default permission mode, an rm or rmdir targeting the working directory or another critical path always requires explicit approval, even if a matching allow rule exists.

Sandboxing, Isolation Boundaries, and Network Controls

KEY CONCEPT

Granting Tool and Web Access Without Exposing Production

Live Read-Along (click any sentence to jump)
Good sandboxing lets an agent run shell commands and search the web without ever exposing production systems or raw credentials. In Claude Managed Agents, the agent loop, session history, and vault secrets all stay outside the container boundary. Bash and file tools run in an isolated per-session Linux container, while web fetch runs server-side, enforces domain allowlists, and only opens URLs that have already appeared in the session.

Sandboxing separates what the agent can execute from the host infrastructure and secrets it must never touch. In Claude Managed Agents, Anthropic enforces this boundary by architecture: the agent loop, session history, and vault secrets live outside the sandbox on Anthropic's servers, while bash and file tools execute inside an isolated per-session Linux container with no shared filesystem state across sessions.

Web tools (web_search and web_fetch) run on Anthropic's servers and are bounded by both per-tool domain allowlists and the environment's limited networking host list. Furthermore, web_fetch only opens URLs that have already appeared in the session, blocking blind arbitrary-URL exfiltration.

ARCHITECTURE PATTERN

Choosing an Isolation Technology for Agent Workloads

Live Read-Along (click any sentence to jump)
When hosting Claude Code or the Agent SDK yourself, match your isolation layer to your threat model. The open-source sandbox runtime gives very low overhead using bubblewrap or Seatbelt, while hardened Docker containers drop all capabilities and set network none. For multi-tenant workloads running untrusted code, step up to gVisor to intercept syscalls in userspace, or Firecracker microVMs that boot in under one hundred twenty-five milliseconds and route all egress over vsock.

EXAM TRAP

Claude Code Bash Sandbox Boundaries and Limitations

Live Read-Along (click any sentence to jump)
On the exam, do not confuse Claude Code's built-in Bash sandbox with full-process isolation. Built-in tools like Read, Write, WebFetch, hooks, and local MCP servers run outside that sandbox. For managed enterprise deployments, lock down escape hatches by setting allowUnsandboxedCommands to false and failIfUnavailable to true so Claude exits rather than silently running unsandboxed. And remember that without TLS inspection, hostname-only proxies can still be bypassed via domain fronting.
  • What runs outside the sandbox: Claude Code's built-in /sandbox wraps Bash, PowerShell, and Monitor commands—but built-in file/web tools (Read, Edit, Write, WebFetch, WebSearch), command hooks, local MCP servers, and mods run outside the sandbox. Putting a path in sandbox denyRead does not block the Read tool; wrap the entire Claude Code process in a container or VM for a unified boundary.
  • Disable escape hatches in managed deployments: By default, Claude can ask to retry a failed command unsandboxed, and if sandbox dependencies are missing at startup Claude falls back to unsandboxed mode. Set sandbox.allowUnsandboxedCommands: false and sandbox.failIfUnavailable: true in managed settings to make sandboxing a hard gate.
  • No TLS inspection by default: The built-in sandbox proxy enforces domain allowlists on the client-supplied hostname without terminating TLS, leaving a theoretical domain fronting vector unless you front egress with a TLS-terminating proxy.
ARCHITECTURE PATTERN

The Proxy Pattern for Zero-Exposure Egress and Credential Injection

Live Read-Along (click any sentence to jump)
The gold-standard production pattern is running the agent container with network none and routing all egress through a host-side proxy over a Unix socket or vsock. The proxy enforces strict domain allowlists, logs traffic, and injects real credentials—using tools like Envoy's credential injector—so secrets never enter the sandbox. Remember that standard HTTPS proxy variables create an opaque tunnel unless you terminate TLS or move authenticated calls behind an external MCP server.

Run an egress proxy outside the agent's container or VM (reached via a mounted Unix socket or vsock while the container runs with --network none). The proxy enforces domain allowlists, logs every request, and injects real auth headers (for example, Envoy's credential_injector filter) so the agent never possesses raw secrets.

  • ANTHROPIC_BASE_URL routes Claude API sampling calls in plaintext HTTP to your local proxy for easy inspection and credential injection.
  • HTTP_PROXY / HTTPS_PROXY routes system-wide traffic, but HTTPS creates an opaque CONNECT tunnel unless you run a TLS-terminating proxy with its CA installed in the container trust store—or expose external services through an MCP server / custom tool running outside the boundary.
  • Watch for runtimes that ignore proxy env vars (e.g., Node.js fetch() requires NODE_USE_ENV_PROXY=1 in Node 24+, and Java Maven/Gradle ignore them); use proxychains or iptables transparent proxying when needed.
SECURITY HARDENING

Filesystem Isolation and Credential Hygiene

Live Read-Along (click any sentence to jump)
Even a read-only mount can cause a major breach if the directory contains dot env files, cloud credentials, kubeconfig, or private keys. Always sanitize or filter workspaces before mounting them into an agent container, use non-executable tmpfs mounts for temporary scratch space, and consider overlay filesystems when you want to inspect every file modification before committing it to persistent storage.
  • Mount code read-only (:ro) whenever an agent only analyzes code, and use ephemeral tmpfs mounts (rw,noexec,nosuid,size=100m) for scratch directories that vanish when the container exits.
  • Use overlay filesystems when an agent must edit files but changes require human or automated review before persisting to the underlying repo.
  • Sanitize before mounting: Even a read-only mount leaks secrets if the workspace contains .env, ~/.aws/credentials, ~/.kube/config, ~/.git-credentials, .npmrc, or *.pem keys. Copy only required source files or apply .dockerignore-style filtering, and scrub inherited subprocess env vars (CLAUDE_CODE_SUBPROCESS_ENV_SCRUB).
Threat Defense and Adversarial Testing for Agentic Systems

Agentic Attack Surface, Lethal Trifecta, and Secure MCP

THREAT MODEL

Prompt Injection, Tool & Memory Poisoning, and Unsafe Autonomy

Live Read-Along (click any sentence to jump)
Tool-using agents face four distinct classes of runtime threats. Direct and indirect prompt injections hijack control flow through user inputs or third-party data like tickets and webpages. Tool poisoning and rug pulls hide directives inside MCP tool descriptions, even steering calls to other servers. Shared memory stores enable persistent memory poisoning across sessions, and unsafe autonomy occurs when a determined agent misuses reachable tools just to get past an obstacle.

Tool-using agents expand the traditional LLM threat surface across four distinct vectors:

  • Direct vs. Indirect Prompt Injection: In direct attacks, the end user is the adversary trying to bypass guardrails. In indirect attacks, a trusted user invokes an agent that reads malicious instructions hidden in emails, tickets, webpages, or OCR text.
  • Tool Poisoning, Shadowing, and Rug Pulls: MCP tool names and descriptions are instructions the model reads. A malicious server can embed hidden directives that steer how the agent calls other servers' tools (shadowing) or silently mutate tool definitions after initial approval (rug pull).
  • Memory Poisoning: In agents sharing a persistent memory store across sessions, a single injected payload can write persistent instructions into memory that hijack future sessions.
  • Unsafe Autonomy: Even without an attacker, an overly capable agent trying to overcome an obstacle may misuse a reachable tool or credential in ways the operator never intended.
KEY CONCEPT

The Lethal Trifecta for AI Agents

Live Read-Along (click any sentence to jump)
Memorize the Lethal Trifecta—it is a centerpiece of Domain seven. Whenever an agent simultaneously has access to private data, processes untrusted input, and can communicate externally, a single indirect prompt injection can silently exfiltrate your data. Stronger system prompts cannot close this loop. You must break or deterministically gate at least one leg outside the model through least-privilege data scoping, strict recipient or domain allowlists, or mandatory human approval.

An agent enters a critical data-exfiltration state whenever a single session simultaneously combines all three capabilities of the Lethal Trifecta:

  1. Access to private data (CRM records, internal repos, secrets, customer PII)
  2. Exposure to untrusted input (inbound emails, support tickets, scraped web pages, external PRs)
  3. External communication capability (sending email, posting webhooks, unrestricted curl/bash egress, or calling external APIs)

Exam Rule: Prompt-level warnings cannot break the Lethal Trifecta. You must remove or deterministically gate at least one leg outside the model—for example, scoping CRM queries to the ticket's own account, enforcing recipient/domain allowlists, or requiring human approval before external sends.

DEFENSE IN DEPTH

Hardening Pipelines Against Indirect Prompt Injection

Live Read-Along (click any sentence to jump)
To harden tool pipelines against indirect prompt injection, always deliver third-party content strictly inside tool result blocks, never in system or user text. JSON-encode untrusted strings so attackers cannot break out of delimiters, label the content's source, and never put your own developer instructions inside a tool result. For high-risk tools, pre-screen raw tool outputs with a lightweight Claude Haiku five point five classifier before returning them to the main agent.
  • Isolate untrusted data in tool_result blocks: Never concatenate third-party content into system prompts or plain user text blocks. Claude is specifically trained to treat tool_result payloads with skepticism.
  • JSON-encode payloads and label provenance: Wrap untrusted strings inside JSON objects (preventing tag/quote breakout) and explicitly state the source (e.g., "source": "inbound_email") in tool descriptions or results.
  • Never place your own instructions inside tool_result: Because Claude treats tool results as untrusted data, developer instructions placed there may be ignored or flagged; place developer guidance in a subsequent user turn or a mid-conversation system message.
  • Screen tool outputs before ingestion: Pass raw tool outputs through a lightweight Claude Haiku 5.5 classifier with structured output_config (injection_suspected: boolean) and return an error or stripped summary if flagged—or if stop_reason: "refusal" occurs. Note that Anthropic's computer use and browser use tools also run built-in injection classifiers on screenshots and page text.
SECURE MCP

MCP Authorization (OAuth 2.1) and Protocol Threat Mitigations

Live Read-Along (click any sentence to jump)
Securing MCP requires strict OAuth two point one hygiene. Remote MCP servers act as OAuth resource servers: they publish Protected Resource Metadata, enforce PKCE with S256, and bind tokens to their exact URL using the RFC 8707 resource parameter. Never allow token passthrough—servers must validate audience claims for themselves. If you run an MCP proxy, prevent confused deputy attacks by enforcing per-client consent before redirecting upstream, and treat local stdio servers as untrusted code.

FRAMEWORKS & RED TEAMING

Red-Team Exercise Design, OWASP LLM Top 10 (2025), and NIST AI RMF

Live Read-Along (click any sentence to jump)
Effective red-teaming tests your entire harness, not just the model: inject poisoned emails and tool outputs to prove your deterministic hooks and egress controls still hold even when the model is fooled. Map your threat model to the 2025 OWASP Top Ten for LLM Applications—especially Prompt Injection, Excessive Agency, Supply Chain, and Sensitive Information Disclosure—and organize ongoing governance around NIST AI RMF's Govern, Map, Measure, and Manage functions with the AI 600-1 Generative AI Profile.
  • Red-team exercise design: Test end-to-end agent workflows before launch using realistic poisoned documents, emails, and tool outputs. Verify both layers: that the model resists embedded instructions and that deterministic hooks, sandboxes, and approval gates block the exploit path when the model fails.
  • OWASP Top 10 for LLM Applications (2025): Anchor threat models to LLM01 (Prompt Injection), LLM02 (Sensitive Information Disclosure), LLM03 (Supply Chain—compromised MCP packages/dependencies), LLM04 (Data and Model Poisoning), LLM05 (Improper Output Handling), LLM06 (Excessive Agency—over-privileged tools and unsafe autonomy), LLM07 (System Prompt Leakage), LLM08 (Vector & Embedding Weaknesses), LLM09 (Misinformation), and LLM10 (Unbounded Consumption).
  • NIST AI RMF 1.0 & NIST AI 600-1 (GenAI Profile): Structure organizational risk governance across Govern, Map, Measure, and Manage—using AI 600-1 to address generative-specific risks such as data privacy, confabulation, information security, and human-AI configuration oversight.
Identity, Secrets, and Audit at Scale

Workload Identity Federation, Vaults, and Compliance Auditing

KEY CONCEPT

Workload Identity Federation (WIF) Replacing Static API Keys

Live Read-Along (click any sentence to jump)
At enterprise scale, replace static API keys with Workload Identity Federation. Your workload presents a short-lived OIDC JWT from Kubernetes, GitHub Actions, or your cloud provider to Anthropic's OAuth token endpoint using the RFC 7523 jwt-bearer grant. Three resources wire this together: a non-human service account, a federation issuer with its JWKS source, and a federation rule that evaluates subject prefixes, claims, or CEL conditions before minting a short-lived access token.

Workload Identity Federation (WIF) eliminates long-lived sk-ant-... static API keys by letting workloads exchange short-lived OIDC JWTs from AWS, GCP, Azure Entra ID, Kubernetes, GitHub Actions, SPIFFE, or Okta for short-lived Anthropic access tokens (sk-ant-oat01-...) via RFC 7523 jwt-bearer at POST /v1/oauth/token.

You configure three Console resources: a Service Account (svac_..., a non-human principal scoped to specific workspaces), a Federation Issuer (fdis_..., with discovery, explicit_url, or inline JWKS for air-gapped clusters), and a Federation Rule (fdrl_..., matching subject_prefix, audience, exact claims, or CEL condition expressions to grant an OAuth scope like workspace:developer and a token_lifetime_seconds between 60 and 86,400).

EXAM TRAP

WIF Credential Precedence, Refresh Windows, and jti_reused Failures

Live Read-Along (click any sentence to jump)
Three WIF operational traps show up frequently in production incidents. First, the Anthropic API key environment variable sits above federation variables in the five-tier credential precedence order, so a leftover key silently overrides WIF—always check ant auth status. Second, the SDK refreshes proactively at minus one hundred twenty seconds and mandatorily at minus thirty seconds. Third, JWTs with a J T I claim are single-use by default, so unrotated token files or retries trigger J T I reused errors.
  • Leftover API key overrides WIF: The SDK resolves credentials in 5 tiers: (1) constructor args, (2) ANTHROPIC_API_KEY / ANTHROPIC_AUTH_TOKEN, (3) explicit ANTHROPIC_PROFILE, (4) federation env vars (ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_IDENTITY_TOKEN_FILE, etc.), (5) implicit active profile. A forgotten ANTHROPIC_API_KEY silently wins over WIF—always verify with ant auth status during migration before deleting the static key.
  • Token lifetime & two-tier refresh: Minted token lifetime is min(rule.token_lifetime_seconds, 2 * remaining_idp_jwt_lifetime) (floor 60s). The SDK performs an advisory refresh at expiry minus 120s (keeps using cached token if endpoint fails) and a mandatory refresh at expiry minus 30s (fails on error).
  • Single-use jti replay protection: By default, JWTs with a jti claim are single-use. If a retry loop or unrotated token file re-presents the same JWT, exchange fails with jti_reused. Rotate projected tokens well ahead of the refresh window; disabling check_jti removes replay protection for the entire issuer and is a last resort.
SECRETS & AGENT IDENTITY

Managed Agents Vaults, Egress Swapping, and Per-Agent JWTs

Live Read-Along (click any sentence to jump)
For third-party credentials, Managed Agents Vaults keep secrets completely out of the sandbox. MCP OAuth credentials are injected server-side with automatic refresh, while environment variable credentials appear in the sandbox as opaque placeholders that the egress gateway swaps into headers only for allowlisted hosts. In self-hosted deployments, you can back vaults with AWS, GCP, Azure, or HashiCorp secret managers and sign short-lived per-agent JWTs so MCP gateways enforce least-privilege access per agent ID.
  • Managed Agents Vaults (vlt_...): Register per-user credentials once (write-only fields never returned by the API) and attach a vault ID per session. Supports MCP credentials (mcp_oauth with automatic token refresh, or static_bearer keyed by mcp_server_url) and environment variable credentials (environment_variable) where the sandbox only sees an opaque placeholder (cma_ph_...) that the egress gateway swaps for the real secret in the Authorization header only on allowlisted hosts.
  • External Secret Managers: Self-hosted Managed Agents can store vault secrets in AWS Secrets Manager, Google Cloud Secret Manager, Azure Key Vault, or HashiCorp Vault via a secret_store prefix, keeping only references in the database. Note that vaults are workspace-scoped; delete the vault or credential to revoke access.
  • Cryptographic Agent Identity: Self-hosted Managed Agents can sign short-lived per-agent JWTs (typ: agent+jwt, token_use: agent, RS256, default 5-minute max exp) sent to MCP gateways via Authorization: Bearer or Agent-Identity-Token. Gateways authorize on agent_id and—when SSO is active—can inspect actor_sub (remembering actor_sub identifies the session creator, not human approval of a specific tool call, and is absent for tool listings and subagents).

SECURITY POSTURE

Auditing Security Posture Events and SIEM Integration

Live Read-Along (click any sentence to jump)
Finally, integrate Security Posture from the Compliance API into your SIEM using OCSF mapping to detect configuration drift. Controls are automatic, manual, or information-only, and admins can record attestations with a default ninety-day review date. Pay close attention to accepted risk attestations, because they report as passed even when the control is off. Also remember that Activity Feed records persist for six years and are not shortened or encrypted by CMEK or ZDR.
  • Three control kinds: The Compliance API exposes Security Center controls as Automatic (e.g., sso_enabled), Manual (e.g., oauth_conditional_access in an external IdP), or Information-only (e.g., allowed_invite_domains, rated descriptive).
  • Attestations & drift: Admins attest controls as completed, accepted_risk, or control_failed (default 90-day review_date). An accepted_risk attestation causes a control to report passed even though the underlying control is not in place—ingest Security Posture events from the Activity Feed into your SIEM (normalized to OCSF) to alert on risky changes and expiring risk acceptances.
  • Retention & privacy caveats: Activity Feed records (including actor user ID, email, IP, and user agent) are retained for 6 years even after user or org deletion. CMEK, ZDR, and HIPAA plans do not encrypt or shorten retention of attestation metadata, and attestation comments are never returned by the API or Activity Feed (and cannot be saved when CMEK or ZDR restricts them).
CCDV-P Scenario Practice

Production Scenario Questions

Scenario 1: Closing the Lethal Trifecta in an Autonomous Procurement Agent

An enterprise deploys a Claude Managed Agent that reads inbound vendor PDF invoices from an external inbox, queries an internal ERP database for purchase orders and bank routing details, and uses an MCP email/webhook tool to notify accounts payable or request vendor clarification. During pre-launch red-teaming, an adversarial invoice embeds hidden instructions that cause the agent to query another vendor's bank details from the ERP and send them to an external attacker address via the email tool. The engineering team has already wrapped the invoice text in XML tags and added a strict system prompt forbidding data exfiltration. Which combination of changes most directly closes the exploit path?

Answer: B — The agent exhibits the Lethal Trifecta (private ERP data + untrusted vendor invoices + external email communication). Prompt-level warnings cannot be relied on as a security boundary. Option B breaks the exploit deterministically outside the model by enforcing least-privilege data scoping on the ERP tool, gating external communication with recipient allowlisting or an always_ask confirmation policy, and following Anthropic's indirect prompt injection hardening (JSON-encoded tool_result blocks). Option A makes injection worse by placing untrusted data in the system prompt; Option C only detects exfiltration after the fact; Option D relies on brittle keyword filtering that is trivially bypassed.

Scenario 2: Debugging a Workload Identity Federation Migration on Kubernetes

A platform team migrates a Kubernetes agent fleet from static workspace API keys to Workload Identity Federation (WIF). They configure the federation issuer, service account, and federation rule, mount projected OIDC service-account tokens at /var/run/secrets/anthropic.com/token, and inject ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, and ANTHROPIC_IDENTITY_TOKEN_FILE into the pods. Initially, usage logs show requests are still authenticating via the old static API key. After removing the static key from the deployment manifest, pods authenticate successfully at startup, but 50 minutes later fail token refresh with jti_reused in the Claude Console authentication history. What explains both issues and what is the cleanest fix?

Answer: A — In the SDK's 5-tier credential precedence, ANTHROPIC_API_KEY sits above federation environment variables, so any leftover key silently overrides WIF (verified via ant auth status). Once the static key was removed, the SDK reread ANTHROPIC_IDENTITY_TOKEN_FILE at its advisory/mandatory refresh window (120s/30s before expiry), but because the projected JWT had not rotated yet, it re-submitted the same single-use jti claim and failed with jti_reused. Rotating the projected token well within the minted token's lifetime fixes the root cause without weakening security. Option B is wrong because zero-argument env resolution is the recommended production pattern and longer lifetime does not solve an unrotated JWT; Option C unnecessarily disables replay protection for the entire issuer; Option D is wrong because every service account is implicitly a member of the default workspace.

Scenario 3: Designing Enterprise DLP Prevention and Compliance Auditing

A regulated financial services company running Claude Enterprise across claude.ai and Claude Code needs three security capabilities: (1) block employees from sending regulated account numbers to Claude before inference runs, without deploying endpoint agents on laptops; (2) automatically redact account numbers from prompts inline so users' chats continue uninterrupted; and (3) retain a 6-year audit trail of all user activity, Security Posture attestation changes, and full local/remote session transcripts (including uploaded non-text files) in their SIEM. A staff engineer proposes enabling Platform Inference Hooks and using an Admin API key against the Compliance API. Which assessment of this proposal is most accurate?

Answer: B — Platform Inference Hooks run server-side across all Claude Enterprise products (including claude.ai and Claude Code) with zero client installation, making them ideal for requirement 1 (inline DLP allow/deny). However, Inference Hooks explicitly do not support rewriting or redacting prompts and do not send raw image/file bytes—so requirement 2 cannot be met by Inference Hooks alone (and users must edit or rewind denied turns to continue). For requirement 3, the Compliance API requires a Compliance Access Key to access session transcripts, files, and Security Posture results; an Admin API key only accesses the Activity Feed. Option A invents prompt rewriting for Inference Hooks; Option C falsely claims Inference Hooks exclude Claude Code and confuses OTel telemetry with inline blocking; Option D confuses post-hoc Compliance API auditing with inline enforcement.
