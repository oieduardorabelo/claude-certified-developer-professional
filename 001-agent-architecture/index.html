Multi-Agent Orchestration

Multi-Agent Topologies, Context Isolation, and Human-in-the-Loop

KEY CONCEPT

When Multi-Agent Architectures Earn Their Token Budget

Live Read-Along (click any sentence to jump)
Multi-agent systems shine when work fans out in parallel across independent sources or exceeds a single context window. Anthropic's research benchmarks showed an Opus lead with Sonnet workers beating a single Opus agent by ninety percent. The catch is cost: multi-agent systems burn roughly fifteen times more tokens than chat, so only reach for them when task value justifies the spend and subtasks truly decouple.

Multi-agent systems excel at breadth-first, parallelizable exploration where information exceeds a single context window or requires distinct toolsets. In Anthropic's internal research evaluations, an orchestrator-worker design (Claude Opus lead with Claude Sonnet subagents) outperformed a single Opus agent by 90.2%, largely because token usage alone explained 80% of performance variance on complex search benchmarks.

The tradeoff is steep: single agents consume roughly 4× the tokens of standard chat, while multi-agent systems consume roughly 15×. Domains with heavy inter-agent dependencies or shared mutable context—like tightly coupled code edits—are poor fits unless subtasks decompose cleanly.

DELEGATION & ISOLATION

Context-Isolation Boundaries and Avoiding the 'Game of Telephone'

Live Read-Along (click any sentence to jump)
By default, a subagent starts with a clean context window—it never sees the parent's conversation history or tool results. That means your delegation prompt must carry the full contract: objective, output format, tools, boundaries, and effort budget. For large artifacts like code or reports, have subagents write directly to the filesystem and pass back lightweight references so you avoid a costly game of telephone through the coordinator.
  • Fresh Context by Default: Non-fork subagents do not inherit parent conversation history, tool results, or the parent's system prompt. They receive only their own AgentDefinition.prompt, the Agent tool prompt string, their tool subset, and project CLAUDE.md (unless omitClaudeMd: true).
  • Explicit Delegation Contracts: Vague prompts cause duplicated searches and missed gaps. Every delegation must specify: (1) objective, (2) output format, (3) tool/source guidance, (4) clear task boundaries, and (5) effort-scaling rules (e.g., 1 agent for simple lookups, 2–4 for comparisons, 10+ for deep research).
  • Bypass the Coordinator for Large Artifacts: To prevent the 'game of telephone' and token bloat, have subagents write structured outputs (code, reports, datasets) directly to a shared filesystem or artifact store and return lightweight references to the lead agent.
  • Forks & Output Scanning: Forked subagents (subagent_type: "fork") copy parent history instead of starting fresh—block them with disallowedTools: ["Agent(fork)"] if strict isolation is required. Claude Code also scans subagent final messages to neutralize imitated control tags (like <system-reminder>) and fake turn markers (Human: / Assistant:).
CODE PATTERN

Least-Privilege Subagent Definition in the Agent SDK

Live Read-Along (click any sentence to jump)
In the Agent SDK, you define specialized subagents programmatically with AgentDefinition. Notice the production guardrails here: a crisp description so the lead routes accurately, read-only tools for least privilege, a Sonnet model override to control cost, max turns to cap runaway loops, and disallowed tools blocking Agent fork when you need strict isolation.
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Agent"],
    disallowed_tools=["Agent(fork)"],  # Enforce strict context isolation
    agents={
        "security-reviewer": AgentDefinition(
            description="Audits auth and crypto code for vulnerabilities.",
            prompt="Review for OWASP flaws. Return file:line findings only.",
            tools=["Read", "Grep", "Glob"],  # Read-only least privilege
            model="sonnet",
            maxTurns=12,      # Bound runaway loops; returns partial if hit
            background=True,  # Non-blocking async_launched execution
        )
    },
)
EXAM TRAP

Inter-Agent Failure Modes: Sync Bottlenecks & Emergent Drift

Live Read-Along (click any sentence to jump)
Watch out for two classic exam traps in multi-agent operations. First, synchronous subagent waits let a single slow worker stall the entire pipeline, while async fan-out demands explicit error handling because API errors aborting a subagent are never returned as normal output. Second, never swap code underneath running stateful agents—use rainbow deployments so in-flight sessions finish on their original version.

Synchronous fan-out bottlenecks: Waiting synchronously for every subagent batch simplifies coordination, but one slow worker blocks the entire lead agent and prevents mid-flight steering. Asynchronous execution unlocks concurrency, yet introduces state consistency and error-propagation hazards—note that in the Agent SDK, an API error (like a rate limit) ending a subagent early is never delivered as its normal result.

Production deployment hazard: Never hard-restart live multi-agent fleets during a release. Use rainbow deployments to shift new traffic gradually while existing stateful sessions drain on their original version.

HUMAN-IN-THE-LOOP

Approval Gates, Clarifying Questions, and Long-Delay Deferral

Live Read-Along (click any sentence to jump)
Human-in-the-loop flows in the Agent SDK center on the can use tool callback, which pauses execution for both tool approvals and Ask User Question prompts. Remember that deny rules, permission modes, and allow rules run before can use tool—so use a Pre Tool Use hook to intercept everything else. And if a human might take hours to approve, return defer from Pre Tool Use so your worker can exit and resume later.
  • canUseTool Callback: Fires in two cases: (1) a tool needs approval after earlier permission checks, or (2) Claude invokes AskUserQuestion to ask clarifying questions. Execution pauses until the callback returns allow (optionally with updatedInput) or deny (with a message Claude sees).
  • Permission Evaluation Order: Deny rules, permission mode (e.g., dontAsk), and allow rules evaluate before canUseTool. To inspect or gate calls that bypass canUseTool (such as working-directory reads), attach a PreToolUse hook.
  • Async Human Delays: Although canUseTool can wait indefinitely, holding a serverless worker or container open for hours is brittle. Instead, return a defer decision from a PreToolUse hook so the process can exit cleanly and resume later from the persisted session, pairing it with a PermissionRequest hook to ping Slack or email.
Durable Execution and State Management

Sessions, Checkpointing, Resumability, and Model Version Continuity

KEY CONCEPT

Designing Agents That Survive Crashes and Compounding Errors

Live Read-Along (click any sentence to jump)
Long-running agents accumulate state across dozens of tool calls, so restarting from scratch after a crash or timeout is unacceptable in production. Durable execution pairs deterministic infrastructure—persisted sessions, file checkpoints, and bounded retries—with Claude's own adaptability when you surface structured tool failures back into the loop.

Long-running agents maintain rich state across dozens or hundreds of tool calls. Restarting from scratch after a transient API timeout, host preemption, or tool failure wastes tokens and degrades user trust. Durable execution combines deterministic safeguards—external session persistence, regular state checkpoints, and bounded retries—with model adaptability, feeding structured tool-failure signals back to Claude so it can recover gracefully.

CODE PATTERN

File Checkpointing and Rewinding in the Agent SDK

Live Read-Along (click any sentence to jump)
To roll back risky file mutations in the Agent SDK, enable file checkpointing and pass replay user messages in extra args so turn-start user messages carry a checkpoint UUID. Capture that UUID alongside the session ID. If validation fails later, resume the session with an empty prompt and call rewind files to restore tracked files to that exact snapshot.
# 1. Enable checkpointing + replay-user-messages to receive restore UUIDs
opts = ClaudeAgentOptions(
    enable_file_checkpointing=True,
    permission_mode="acceptEdits",
    extra_args={"replay-user-messages": None},
)
checkpoint_id, session_id = None, None
async with ClaudeSDKClient(opts) as client:
    await client.query("Refactor auth module")
    async for msg in client.receive_response():
        if isinstance(msg, UserMessage) and msg.uuid and not checkpoint_id:
            checkpoint_id = msg.uuid      # Turn-start prompt UUID
        if isinstance(msg, ResultMessage):
            session_id = msg.session_id

# 2. Rewind later by resuming with an empty prompt and calling rewind_files
async with ClaudeSDKClient(
    ClaudeAgentOptions(enable_file_checkpointing=True, resume=session_id)
) as client:
    await client.query("")
    async for _ in client.receive_response():
        await client.rewind_files(checkpoint_id)
        break
EXAM TRAP

What Sessions and File Checkpointing Do NOT Track

Live Read-Along (click any sentence to jump)
This distinction is a favorite exam trap: sessions persist conversation history, not disk state, while rewind files restores disk state without rewinding conversation history. Even more importantly, file checkpointing only tracks Write, Edit, and Notebook Edit in the main conversation. It will not undo Bash commands like sed in place, it ignores subagent edits, and it skips symlinks.

Two separate planes of state: Sessions persist the conversation, not the filesystem. Conversely, rewindFiles() restores files on disk while leaving conversation history intact.

Blind spots in file checkpointing: Checkpointing only backs up files modified by Write, Edit, and NotebookEdit in the main conversation. It does not undo changes made via Bash (such as sed -i or shell scripts) unless those files were already tracked, does not track subagent edits, and safely skips symlinks, hard links, or moved parent directories (reported in RewindFilesResult.skippedLinks).

MODEL CONTINUITY

Surviving Model Version Upgrades and Cross-Model Fallbacks

Live Read-Along (click any sentence to jump)
Durable agents must also survive model version upgrades and fallbacks mid-session. Always keep sending the full unmodified history: if a fallback model cannot read prior thinking blocks, the API drops them silently for that turn and restores them when you switch back. Just remember to replace thinking type enabled with adaptive on preserved-thinking models, or you will hit a four hundred error.
  • Never Strip Thinking Blocks on Model Switches: On models with preserved thinking (e.g., Claude Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable/Mythos 5.1–5.2), keep sending the full unmodified conversation when switching models or cloud accounts. If the target model cannot read an earlier model's thinking blocks, the API drops them silently for that turn without error or billing—and reads them again if you switch back.
  • Adaptive vs. Enabled Thinking: Preserved-thinking models return a 400 error if you send thinking: {"type": "enabled"}. When migrating a live session from an older model, switch to thinking: {"type": "adaptive"} (or omit thinking).
  • Cross-Model System Message Parity: If a fallback routes to a model that does not accept mid-conversation system messages (such as Claude Sonnet 5), omit those messages only from that request while keeping them in your stored transcript. Returning to a supporting model without them mutates the prefix and triggers a 400 prefix-check error.
  • Version Pinning in Managed Agents: Pass {"type": "agent", "id": agent.id, "version": 2} when creating sessions or listing predefined subagents so live runs stay pinned while you stage new agent versions independently.
Architecture Selection at Scale

Evolving Between Workflows and Agents, and Selecting the Right Harness

KEY CONCEPT

Workflows vs. Agents: Earn Every Layer of Autonomy

Live Read-Along (click any sentence to jump)
Anthropic draws a sharp boundary between workflows and agents. Workflows orchestrate Claude along predefined code paths, giving you predictable latency, lower cost, and tight control. Agents let Claude drive its own tool loop from environmental ground truth. As a staff engineer, you start with the simplest augmented LLM or workflow and only pay the autonomy tax when production quality data proves a fixed path cannot handle the task.

Anthropic draws a sharp architectural line between workflows (LLMs and tools orchestrated through predefined code paths) and agents (LLMs dynamically directing their own loop and tool usage based on environment ground truth). Start with the simplest solution—often a single augmented LLM call with retrieval and tools—and only escalate complexity when production quality data proves simpler patterns fall short.

Workflows win on predictability, bounded latency, and unit cost for well-defined tasks. Agents win when step counts are unpredictable, tasks are open-ended, and environment feedback (test suites, tool outputs) lets Claude verify progress and recover autonomously.

REUSABLE STANDARDS

Framework Discipline and Agent-Computer Interface (ACI) Standards

Live Read-Along (click any sentence to jump)
When setting team standards, resist heavy third-party frameworks that hide raw prompts and break cache visibility. Instead, invest in your Agent-Computer Interface. Keep tool sets minimal and non-overlapping, poka-yoke parameters like requiring absolute file paths, and avoid awkward escaping overhead. Anthropic even found that having an agent test and rewrite unclear MCP tool descriptions cut task completion time by forty percent.
  • Avoid Opaque Framework Bloat: Heavy third-party frameworks often obscure exact prompts, tool schemas, and cache boundaries, slowing production debugging. Standardize on thin, transparent abstractions directly over the Claude APIs or Agent SDK so engineers understand what crosses the wire.
  • Invest in the Agent-Computer Interface (ACI): Treat tool definitions with the same rigor as human-computer interfaces. Give every tool a distinct, non-overlapping purpose, concrete examples, edge-case notes, and clear boundaries.
  • Poka-Yoke Tool Parameters: Design arguments so mistakes are structurally impossible—for example, requiring absolute filepaths instead of relative paths, avoiding brittle line-count diff headers, and avoiding JSON-escaped code strings where natural formats work better.
  • Test Tools with Agents: Running an automated tool-testing agent to exercise flawed MCP tools and rewrite their descriptions cut downstream task completion time by 40% in Anthropic's research.
EXAM TRAP

De-Escalating an Agent Back to a Workflow

Live Read-Along (click any sentence to jump)
Do not assume architecture evolution only moves toward more autonomy. If production traces show an expensive autonomous agent executing the exact same three tool calls ninety-five percent of the time, the staff-level move is to de-escalate it into a deterministic routing and prompt-chaining workflow, reserving the agent loop strictly for the unpredictable five percent tail.

Architecture evolution is bidirectional. On the exam, if production telemetry shows an autonomous agent following the exact same three-step tool sequence on 95% of requests while burning excess tokens and missing p95 latency SLOs, the right move is to demote it to a deterministic workflow (such as Routing + Prompt Chaining) and reserve the agentic path only for the 5% long-tail exceptions.

Conversely, escalate a workflow to an agent only when branching logic becomes unmaintainable, tasks are genuinely path-dependent, and objective ground-truth verification exists.

Context and Memory Architecture

Compaction, Context Editing, Persistent Memory, and Tool Context Scaling

KEY CONCEPT

Combating Context Rot with Just-in-Time Context Engineering

Live Read-Along (click any sentence to jump)
Waiting for larger context windows does not solve context rot. Because transformer attention stretches across every token pair, recall degrades well before you hit the hard limit. Treat context as a finite attention budget: write right-altitude system prompts, and favor just-in-time retrieval where agents hold lightweight pointers and pull details on demand.

Because transformer attention scales quadratically (n² pairwise token relationships), every model experiences context rot: recall accuracy and reasoning precision degrade gradually as token count grows, long before hitting the hard context limit. Context engineering treats the window as a finite attention budget, curating the smallest set of high-signal tokens at every turn.

Write system prompts at the right altitude—neither brittle hardcoded if-else scripts nor vague platitudes—and prefer just-in-time retrieval (holding lightweight file paths or queries and loading details on demand via progressive disclosure) or a hybrid strategy (like Claude Code loading CLAUDE.md upfront while exploring files via Glob and Grep).

EXAM TRAP

Preserved Thinking Prefix Checks and Sensitive Content Redaction

Live Read-Along (click any sentence to jump)
Here is a subtle production trap: on preserved-thinking models, thinking blocks are cryptographically tied to everything before them. If your client code edits an earlier message, system prompt, or tool schema, you trigger a four hundred error saying the block is bound to a different conversation. Always use server-side context management or append-only system messages—and if you ever redact secrets from history, strip all subsequent thinking blocks too.

Why client-side history rewrites break preserved thinking: On preserved-thinking models, every thinking block is cryptographically bound to the exact system, tools, and prior messages before it. Mutating earlier turns client-side fails the prefix check and throws a 400 error (The block is bound to a different conversation) unless you either use server-side context editing/compaction, append mid-conversation system messages, or set prefix_mismatch_behavior: "drop_block" (auditing drops via input_transformations).

Redacting secrets or prompt injections: If you must scrub secrets, PII, or injected text from an earlier turn, you must also remove every thinking block after the first place that sensitive content appeared.

Production Scenario Questions

Scenario 1: Multi-Agent Approval Bottleneck & Context Bloat

A platform team runs an Agent SDK incident-triage service inside autoscaled serverless containers with a 15-minute execution timeout. When the lead agent spawns a remediation subagent that needs human approval for a production database change, the container blocks inside the `canUseTool` callback and times out before the on-call engineer responds. Meanwhile, traces show the lead agent's context window is filling up because subagents return 40KB raw log dumps in their final messages. Which architectural change resolves both issues?

Answer: B — Returning `defer` from a `PreToolUse` hook lets the serverless process exit cleanly while waiting for an asynchronous human approval, and a shared `SessionStore` (implementing `append`, `load`, and `listSubkeys`) allows any container replica to resume the session once approved. Having subagents write bulky raw logs to external/shared storage and pass lightweight references eliminates the 'game of telephone' context bloat. (A) wastes compute and `Agent(fork)` worsens context bloat; (C) removes the required human approval guardrail; (D) mixes SDK `canUseTool` semantics with Managed Agents and does not address the 40KB subagent payload bloat.

Scenario 2: Cache Thrashing & 400 Errors on a Preserved-Thinking Agent

A financial compliance agent on `claude-opus-5-5` connects to 80 internal MCP tools and runs 40-turn investigations. Mid-session, once a user completes step-up authentication, the backend updates the top-level `system` prompt with new policy rules, adds 3 privileged tools to the top-level `tools` array, and strips old `tool_result` blocks from the client's `messages` array to save tokens. After migrating to `claude-opus-5-5`, prompt cache hit rates dropped near zero and requests began failing with HTTP 400 (`The block is bound to a different conversation`). What is the best fix?

Answer: C — Editing top-level `system`, `tools`, or earlier `messages` client-side both invalidates the cached prefix and breaks the preserved-thinking prefix check on `claude-opus-5-5`. Declaring the tool catalog upfront with `defer_loading: true` (and Tool Search for the 80-tool catalog), applying post-auth policy and tool changes via an appended `role: "system"` message with `tool_addition` blocks, and using server-side context editing (`clear_tool_uses_20250919`) or on-demand compaction keeps the prefix intact, preserves thinking blocks, and restores cache hits. (A) triggers a 400 error because preserved-thinking models reject `thinking: {"type": "enabled"}`; (B) still destroys prompt caching and loses reasoning; (D) drops full conversation continuity and cache reuse.

Scenario 3: File Rewind Gap & Architecture De-Escalation

An engineering team built a multi-agent code-remediation service using the Agent SDK with `enable_file_checkpointing=True`. Post-incident review reveals two problems: (1) when a validation check failed and the service called `rewind_files(checkpoint_id)`, edits made by a worker subagent and by a `Bash` command running `sed -i` remained on disk; (2) trace analysis shows 96% of tickets follow the exact same 3-step sequence (classify ticket, run static rule fix, open PR) yet cost 12x more than budget. What should the team do?

Answer: A — Agent SDK file checkpointing only tracks `Write`, `Edit`, and `NotebookEdit` in the main conversation—it never undoes `Bash` (`sed -i`) commands or subagent file edits—so deterministic VCS/sandbox isolation (like git worktrees) is required for complete rollback. Simultaneously, production telemetry showing 96% identical 3-step execution is a textbook signal to de-escalate the common path to a predictable, low-cost Routing + Prompt Chaining workflow while keeping the agent for genuinely open-ended edge cases. (B) is factually false about `replay-user-messages`; (C) confuses conversation sessions with filesystem state; (D) does not fix local repo rollback or remove unnecessary agentic overhead.
