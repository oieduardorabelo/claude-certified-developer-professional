Telemetry and Instrumentation

Distributed Tracing & Token Instrumentation

ARCHITECTURE PATTERN

Combining SDK and API OpenTelemetry Spans

Live Read-Along (click any sentence to jump)
To get full end-to-end visibility, combine Anthropic SDK tracing with Claude API tracing. The SDK emits client spans for your app and local tool runner, while the API emits server spans for each internal model run and server tool. Passing the W3C traceparent header links them into one unified trace, and even propagates context into your downstream MCP servers.

Claude supports OpenTelemetry (OTel) tracing from both the Anthropic SDK (emitting CLIENT spans from your application) and the Claude API (emitting SERVER spans with service.name = claude-platform to an OTLP/HTTP protobuf destination on port 443). Running both together connects your app, client-side tools, and Anthropic's internal model runs into one unified trace via the W3C traceparent header.

When using the Messages API or Managed Agents MCP connectors, the Claude API forwards traceparent inside params._meta of tools/call requests so your downstream MCP server spans nest directly under anthropic.mcp_tool_use.

SPAN HIERARCHY

Span Models Across Messages API, Managed Agents, and Agent SDK

Live Read-Along (click any sentence to jump)
Each Claude runtime has a distinct span hierarchy. Messages API traces nest model requests, server tools, and compactions under anthropic dot messages dot create. Managed Agents sessions span multiple traces, so you group a thread by gen A I conversation ID and the whole session by anthropic session ID. In the Agent SDK, the underlying Claude Code CLI emits interaction, LLM request, and tool spans when enhanced telemetry is enabled.

TOKEN & COST METRICS

Counting Tokens Accurately Without Double-Counting

Live Read-Along (click any sentence to jump)
Token accounting in traces has subtle traps. Always sum a single span source per request, preferring API server spans because they capture billed tokens even on canceled calls. Remember that gen A I usage input tokens already includes cache reads and writes, whereas compaction tokens are tracked separately. Finally, deduplicate retried spans using trace ID and span ID.
  • Single source per request: When both SDK (CLIENT) and API (SERVER) spans exist for anthropic.messages.create, sum only the API spans—they reflect billed tokens even on failed or canceled requests, whereas SDK spans can undercount or omit tokens on aborts.
  • Avoid parent-child duplication: For Messages API spans, sum either anthropic.messages.create or its child anthropic.model_request spans—never both. For Managed Agents, sum anthropic.model_request plus anthropic.session.outcome_evaluation.
  • Cache & compaction semantics: gen_ai.usage.input_tokens already includes cache reads and cache writes, so do not add cache attributes on top. Conversely, compaction tokens (anthropic.usage.compaction.* or anthropic.compaction spans) are separate and must be added.
  • Deduplicate deliveries: API OTel export is at-least-once and best-effort; deduplicate spans by trace_id + span_id, and never sum anthropic.messages.count_tokens (not billed usage).
  • Claude Code OTel metrics: Exported via OTEL_METRICS_EXPORTER as claude_code.cost.usage (USD) and claude_code.token.usage (split by type: input, output, cacheRead, cacheCreation—here input excludes cache tokens).
GROUNDING & STRUCTURED LOGS

Reasoning Traceability, Structured Log Events, and User Attribution

Live Read-Along (click any sentence to jump)
For reasoning and grounding traceability, OpenTelemetry maps thinking blocks to reasoning parts and tracks reasoning output tokens separately, while structured log events correlate prompts, tool decisions, and subagent runs via prompt ID and agent ID. To attribute activity to end users safely, pass an opaque ID in W3C baggage, because the Claude API automatically drops any user ID that looks like an email address.

Under OpenTelemetry GenAI semantic conventions, Anthropic content blocks map cleanly for reasoning and grounding audits: thinking blocks become reasoning message parts (with signatures stripped, and token counts in gen_ai.usage.reasoning.output_tokens), while tool_use and tool_result blocks map to tool_call and tool_call_response. Note that Managed Agents spans omit thinking text because agent.thinking events do not expose raw thinking content.

In Claude Code and the Agent SDK, structured log events (OTEL_LOGS_EXPORTER=otlp) emit claude_code.user_prompt, claude_code.api_request, claude_code.tool_decision, and claude_code.tool_result correlated by prompt.id, workflow.run_id, and subagent agent_id / parent_agent_id. To attribute actions to end users, pass an opaque ID via W3C baggage: user.id=4f2a on the Claude API (the API drops any user.id containing an email address for privacy) or percent-encoded enduser.id and tenant.id in OTEL_RESOURCE_ATTRIBUTES for the Agent SDK.

CODE PATTERN

Propagating Trace Context & Tuning Agent SDK Flush Intervals

Live Read-Along (click any sentence to jump)
Here are two production instrumentation patterns. First, wrap Anthropic SDK calls inside your application's active span so the SDK automatically injects traceparent and nests API spans underneath. Second, in the Agent SDK, always use the OTLP exporter rather than console, and lower the export intervals to one thousand milliseconds so short-lived tasks flush before the child process exits.
# 1. Anthropic SDK: nest API spans under your application span
from opentelemetry import trace
from anthropic import Anthropic

tracer = trace.get_tracer("checkout-service")
client = Anthropic()

with tracer.start_as_current_span("handle_support_ticket"):
    # SDK emits CLIENT span and injects W3C traceparent -> API emits SERVER child span
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=1024,
        messages=[{"role": "user", "content": "Check order #4821"}]
    )

# 2. Agent SDK: configure OTLP export + fast flush for short-lived queries
OTEL_ENV = {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",
    "OTEL_TRACES_EXPORTER": "otlp",   # NEVER 'console' (corrupts SDK stdout pipe!)
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.internal:4318",
    "OTEL_TRACES_EXPORT_INTERVAL": "1000",
    "OTEL_METRIC_EXPORT_INTERVAL": "1000",
    "OTEL_RESOURCE_ATTRIBUTES": "enduser.id=usr_92f1,tenant.id=acme"
}
EXAM TRAP

Three Classic Instrumentation Pitfalls

Live Read-Along (click any sentence to jump)
Watch out for three exam traps here. Never configure the console exporter in the Agent SDK because it writes to standard out and breaks the CLI message pipe. In TypeScript, remember to spread process dot env when passing options dot env. And never rely on best-effort OpenTelemetry spans for billing reconciliation or leaked-key audits—use the Usage and Cost Analytics API instead.

1. Never use console exporter in the Agent SDK: The Agent SDK communicates with the Claude Code CLI over stdout; setting console as an exporter corrupts the message channel. Point OTLP at a local collector instead, and use CLAUDE_CODE_OTEL_DIAG_STDERR=1 to surface silent export errors.

2. TypeScript options.env replaces process.env: Unlike Python (which merges), TypeScript Agent SDK env overwrites inherited variables—always spread ...process.env or you will drop PATH and ANTHROPIC_API_KEY.

3. OTel spans are best-effort, not billing-complete: Lost spans or callers disabling the traceparent sampled flag will omit requests. For authoritative spend or leaked-key detection, use the Usage and Cost Analytics API.

Telemetry and Instrumentation

Cache Diagnostics & Privacy-Constrained Content Capture

CACHE DIAGNOSTICS

Pinpointing Prompt Prefix Divergence with Cache Diagnostics

Live Read-Along (click any sentence to jump)
When prompt cache hit rates suddenly collapse, Cache Diagnostics eliminates guesswork. You opt in on turn one by passing a diagnostics object with previous message ID set to null, then thread each response ID into the next turn. Anthropic compares lightweight cryptographic hash fingerprints without storing raw prompts, keeping the feature ZDR-qualified while pinpointing the exact first point of prefix divergence.

Prompt caching requires a byte-for-byte identical prefix. Without diagnostics, a reordered tool, interpolated timestamp, or edited message only shows up as usage.cache_read_input_tokens dropping to zero. The Messages API Cache Diagnostics feature solves this by accepting a diagnostics object on every turn: pass {"previous_message_id": null} on turn 1 to opt in, and pass the previous response's id on every subsequent turn.

The API stores a short-lived, workspace-scoped fingerprint made strictly of cryptographic hashes and token-count estimates—never raw prompt text—making Cache Diagnostics ZDR-eligible (qualified). It is best-effort and never blocks or fails a request.

DIAGNOSTIC MATRIX

Interpreting cache_miss_reason Alongside Usage Tokens

Live Read-Along (click any sentence to jump)
Cache miss reason reports only the earliest divergence: model changed, system changed, tools changed, or messages changed, along with an estimated count of missed input tokens. Always read it alongside cache read input tokens. If diagnostics is null but cache reads are zero, your prompt didn't diverge—the cache entry simply expired or fell below the minimum cacheable length.
diagnostics.cache_miss_reason.typeRoot Cause & Fix
model_changedRouter, A/B test, or fallback switched models; caches are per-model. Hold the model constant per conversation.
system_changedDynamic value (timestamp, request ID) interpolated into system. Keep system byte-stable; move dynamic data to the latest user message.
tools_changedTools added, removed, reordered, or JSON schema keys serialized non-deterministically. Send a fixed tool list with sorted keys.
messages_changedHistory truncated, edited, or assistant/tool_result blocks re-serialized differently. Keep history append-only and echo blocks verbatim.
previous_message_not_found / unavailableNo comparison produced (previous turn omitted diagnostics, different workspace, expired fingerprint, or prompt-affecting params like thinking/tool_choice/beta headers changed).

Reading with usage: If diagnostics is null (no divergence) and cache_read_input_tokens is zero, the prefix matched but the cache entry either expired (5m/1h TTL) or fell below the minimum cacheable token length. If cache_miss_reason is null inside a non-null diagnostics object, the comparison was still pending—check the next turn.

CONTENT CAPTURE

Configuring Content Modes, Truncation, and Opt-In Flags

Live Read-Along (click any sentence to jump)
Telemetry is metadata-only by default across both the Claude API and the Agent SDK. Turning on full content gives you prompts, responses, and tool arguments for debugging and eval pipelines, capped at zero point seven five megabytes per span unless you raise max content bytes. In Claude Code and the Agent SDK, you control sensitivity granularly using opt-in flags for prompts, tool details, tool content, or raw API bodies.
  • API & SDK Content Modes: Default is metadata_only (IDs, timing, status, token counts, agent/tool names). Opt into content (Full content) to capture gen_ai.system_instructions, gen_ai.input.messages, gen_ai.output.messages, and tool arguments/results for debugging and evals.
  • Payload size limits: Full content defaults to 0.75 MB per span (fits a 200k-token context under common 1 MB collector limits; a 1M-token context needs ~4 MB via traces.max_content_bytes). Over-limit spans set anthropic.content.truncated=true, dropping system prompt and earliest messages first on requests, and trailing blocks on tool results.
  • Claude Code / Agent SDK privacy gates: Structural by default; content requires explicit opt-in via OTEL_LOG_USER_PROMPTS=1, OTEL_LOG_TOOL_DETAILS=1 (un-redacts custom agent, skill, plugin, and MCP names), OTEL_LOG_TOOL_CONTENT=1 (tool outputs, 60 KB default cap), or OTEL_LOG_RAW_API_BODIES=1 / file:<dir> (full request/response JSON with thinking redacted).
PRIVACY & COMPLIANCE

Zero Data Retention (ZDR), HIPAA, and CMEK Constraints

Live Read-Along (click any sentence to jump)
Privacy arrangements directly shape what you can instrument. Under ZDR, Messages API full-content OpenTelemetry export still works because spans are buffered only in memory before delivery, whereas HIPAA, FERPA, or K-12 restrictions force API destinations to metadata-only. Remember that customer-managed encryption keys and ZDR cannot share a workspace—CMEK requires standard thirty-day retention on a non-default workspace, and hosted Managed Agents is never ZDR or HIPAA eligible.
ConstraintTelemetry & Retention Behavior
ZDR (Messages API)Prompts/outputs are not stored at rest. Full-content OTel export is permitted—the API holds exported content only in memory until delivery. Once delivered, your observability vendor's retention policy governs it.
HIPAA / FERPA / K-12API telemetry destinations export metadata only regardless of content mode setting (SDK spans in your own VPC are unaffected). Non-HIPAA features return 400 invalid_request_error. Never put PHI in strict: true JSON schemas (schemas are cached up to 24h without PHI protections).
CMEK + ZDRCannot share a workspace on Claude Platform. CMEK encrypts stored data and requires Standard data retention (30 days). A ZDR org can enable 30-day retention and attach a CMEK key to a non-default workspace while keeping other workspaces on ZDR.
Managed Agents & Covered ModelsHosted Managed Agents is not ZDR or HIPAA eligible (stateful transcripts persist until deleted; self-hosted Managed Agents is ZDR-eligible). Covered Models (e.g., Fable 5, Mythos 5) require 30-day retention and reject ZDR workspaces with HTTP 400.
EXAM TRAP

ZDR Does Not Block Stateful Features—HIPAA Does

Live Read-Along (click any sentence to jump)
Here is a critical compliance distinction for the exam. Under HIPAA readiness, Anthropic actively blocks non-eligible features with a 400 error. Under ZDR, calling stateful features like Batch processing, the Files API, or Code Execution is not blocked—you silently step outside ZDR for that data. Always enforce feature allowlists in your gateway if strict ZDR is required.

Under HIPAA readiness, calling a non-eligible feature (like code_execution or Managed Agents) is automatically rejected with HTTP 400 invalid_request_error. Under ZDR, however, the API does not block stateful non-ZDR features such as the Batch API (29-day retention), Files API, or Code Execution (30-day container retention)—calling them silently steps outside your ZDR arrangement for that data! Also note that ZDR is enabled per organization and does not automatically inherit into newly created organizations.

SLIs, SLOs, Cost Analytics & Drift Detection

LLM SLIs & SLOs

Defining Meaningful SLIs Beyond HTTP Availability

Live Read-Along (click any sentence to jump)
Traditional HTTP 200 uptime is dangerously blind for LLM services. Staff engineers define multi-dimensional SLIs: time-to-first-chunk separate from total agent-turn latency, stop-reason ratios that catch max-tokens truncations and safety refusals, prompt cache hit rates that guard unit economics, and task-level quality signals like tool success rate and groundedness.
  • Latency SLIs (split interactive vs. total): Track streaming time-to-first-chunk (gen_ai.response.time_to_first_chunk) separately from end-to-end turn completion and tool-execution latency (claude_code.tool.execution vs. human wait in blocked_on_user).
  • Completion & Stop-Reason SLIs: Monitor the proportion of responses ending in end_turn versus pathological stops: max_tokens (silent truncation), refusal (safety over-triggering), or requires_action timeouts in Managed Agents.
  • Efficiency & Cost SLIs: Track prompt cache hit ratio (cache_read_input_tokens / total_input_tokens), tokens per successful task, and cost per resolved ticket—a 15% cache-hit drop can double spend without triggering any error alert.
  • Quality & Grounding SLIs: Combine deterministic checks (JSON schema validity, tool-call success rate, citation presence) with sampled online LLM-as-judge groundedness and user-acceptance metrics (such as edit acceptance rate).
COST TELEMETRY

Usage and Cost Analytics API for Authoritative Spend & Attribution

Live Read-Along (click any sentence to jump)
When you need authoritative spend tracking and chargeback, query the Usage and Cost Analytics API rather than summing best-effort trace spans. It exposes both token usage and USD cost endpoints with one-minute, hourly, or daily buckets, grouping by up to five dimensions like model, workspace, API key, actor, or Managed Agents session ID, with typical data freshness within four hours.

For executive dashboards, chargeback, and anomaly detection, use the Usage and Cost Analytics API (GET /v1/organizations/analytics/usage and /cost, beta header analytics-usage-cost-2026-08-24, authenticated with an Admin API key, OAuth org:admin / Workload Identity Federation token, or Enterprise read:analytics key). Unlike best-effort OTel spans, it captures 100% of billable usage—including requests with tracing disabled—typically appearing within 4 hours.

You can bucket time series by 1m, 1h, or 1d (with order_by=time) and group by up to 5 dimensions simultaneously, including model, workspace_id, api_key_id, actor, service_tier, agent_id, and session_id. Use api_key_ids[] to audit every request authenticated by a key (ideal for spotting a leaked key), and actor_ids[] to attribute spend to a user or service account.

ALERTING & HEALTH

Designing Actionable Alerts and Protecting Telemetry Pipelines

Live Read-Along (click any sentence to jump)
Good alerting separates urgent burn-rate pages from slow-burn tickets, and monitors the observability pipeline itself. Remember that Claude API OpenTelemetry destinations auto-disable after any 3xx redirect or twenty-four hours of delivery failures, silently dropping spans until re-enabled. To stop runaway agent spend, pair anomaly alerts with platform-enforced session budgets instead of fragile client polling.
  • Multi-window burn-rate alerts: Page on fast error-budget burn (e.g., 2% of monthly SLO burned in 1 hour) for error spikes, refusal surges, or TTFT regressions; route slow drift (gradual cache-hit decay or rising tokens-per-turn) to tickets rather than pages.
  • Watch OTel destination health: In Claude Console, API destinations report Healthy, Failing, No data, or Disabled. The API automatically disables a destination if it returns a 3xx redirect or fails all deliveries for 24 hours—and drops spans while disabled. Alert on ingestion silence!
  • Detecting anomalous usage: Combine real-time OTel rate alerts (runaway agent loop multiplying turns per session) with Analytics API api_key_id / actor anomaly detection (leaked key or unexpected service_tier shift) and hard Managed Agents session budgets rather than client-side polling.
DRIFT & REGRESSIONS

Detecting Quality Drift and Behavioral Regressions After Model Updates

Live Read-Along (click any sentence to jump)
Model updates and fallbacks can degrade quality without raising a single HTTP error. Always compare gen A I request model against gen A I response model on your dashboards so alias rollovers and fallbacks are immediately visible. Track behavioral proxies—like output length shifts, reasoning token ratios, tool retry spikes, refusal rates, and user edit acceptance—to catch drift days before customers complain.

Silent behavioral drift frequently follows a model alias rollover, a fallback activation, or an upstream prompt/tool edit. Always log and dashboard both gen_ai.request.model and gen_ai.response.model—any divergence reveals an alias resolution or fallback model serving live traffic.

To catch regressions before users churn, monitor leading behavioral proxies stratified by gen_ai.response.model: output-token distribution shifts (verbosity inflation or sudden truncation), reasoning-token ratio (gen_ai.usage.reasoning.output_tokens / output_tokens), tool-call frequency and retry rates, refusal rates, and user-side feedback (such as Claude Code Edit/Write acceptance rate dropping from 90% to 72%). Pair proxy alerts with continuous online evaluation on a stratified live-traffic sample.

CODE PATTERN

Querying Hourly Spend Anomalies by API Key and Model

Live Read-Along (click any sentence to jump)
This Python snippet queries the Usage and Cost Analytics API for hourly cost buckets grouped by API key, model, and service tier. Running a scheduled check like this against rolling baselines quickly surfaces leaked keys, unexpected fallback model traffic, or sudden service-tier cost jumps.
import anthropic

# Uses Admin API key or OAuth bearer token (org:admin)
client = anthropic.Anthropic()

rows = client.beta.organization.analytics.cost.list(
    starting_at="2026-10-20T00:00:00Z",
    ending_at="2026-10-21T00:00:00Z",
    time_bucket_width="1h",
    group_by=["api_key_id", "model", "service_tier"],
    order_by="time",
    limit=100,
)

for row in rows:
    # Spot leaked keys, unexpected fallback models, or tier shifts
    print(
        f"{row.starting_at} | key={row.group.api_key_id} "
        f"model={row.group.model} tier={row.group.service_tier} "
        f"usd={row.cost.amount}"
    )
Trace Analysis at Scale

Sampling Strategies, Aggregation & Failure-Cohort Analysis

SCALE CHALLENGE

Why Individual Trace Inspection Breaks Down at Production Volume

Live Read-Along (click any sentence to jump)
At production volume, inspecting individual traces cannot uncover a one-percent systemic bug buried in millions of requests, and storing full-content traces for every call explodes observability bills. Scaling trace analysis requires combining smart sampling with low-cardinality aggregation and structured failure-cohort slicing—while remembering that turning off the W3C traceparent sampled flag suppresses Claude API and MCP spans altogether.

Inspecting one trace at a time works in staging, but at thousands of agent loops per minute, full-content traces generate gigabytes of telemetry per hour and hide 0.5%–2% systemic failure modes inside sea-of-green averages. Effective trace analysis at scale requires three coordinated layers: intelligent sampling so rare failures are never dropped, low-cardinality metric aggregation for fast alerting, and failure-cohort analysis to quantify root causes across populations of traces.

Note how W3C traceparent interacts with Claude API sampling: if your client or gateway clears the sampled flag in traceparent, the Claude API emits no spans for that request and withholds traceparent from downstream MCP connector calls.

SAMPLING STRATEGIES

Head-Based vs. Tail-Based Sampling for Agent Workloads

Live Read-Along (click any sentence to jump)
Choosing between head-based and tail-based sampling is a classic architectural tradeoff. Head-based sampling decides up front at the root span, which is cheap but randomly discards most rare failures. Tail-based sampling buffers completed traces in an OpenTelemetry Collector so you can keep one hundred percent of errors, latency outliers, refusals, and cache misses alongside a small baseline sample of healthy traffic.
DimensionHead-Based SamplingTail-Based Sampling (OTel Collector)
Decision pointAt trace root (before the agent loop runs), e.g., 5% random via traceparent sampled flag.After the entire trace completes and buffers in a trace-ID-aware OTel Collector tier.
StrengthsMinimal compute/memory overhead; cuts Claude API and MCP span volume at the source.Retains 100% of interesting traces: any ERROR status, high latency (e.g., p99), refusal / max_tokens stops, cache misses, or multi-turn loops exceeding turn thresholds—plus a 1–5% baseline of healthy traces.
Failure modeRandomly drops 95% of rare 1% failures, making intermittent tool or edge-case bugs nearly impossible to diagnose.Requires trace-ID-consistent load balancing (so all spans of a trace hit the same collector) and sufficient memory/timeout windows for long-running agent sessions.
AGGREGATION AT SCALE

Cardinality Discipline and Multi-Trace Session Reconstruction

Live Read-Along (click any sentence to jump)
When aggregating telemetry at scale, enforce strict cardinality discipline. Keep unbounded identifiers like prompt ID, session ID, and workflow run ID on traces and log events, while restricting metric labels to low-cardinality dimensions like model, stop reason, and error type. For multi-turn Managed Agents sessions that span several traces, roll up metrics by anthropic session ID and reconstruct thread timelines using gen A I conversation ID.
  • Separate metrics from trace/event attributes: Never attach unbounded identifiers—such as prompt.id, session.id, workflow.run_id, agent_id, or raw user.id—as Prometheus metric labels, or you will trigger cardinality explosions. Keep those on trace spans and structured log events, and use low-cardinality dimensions (model, service_tier, stop_reason, tool_name, error.type) on metrics.
  • Reconstruct multi-trace sessions: Long-running Managed Agents sessions often span multiple independent traces (each user reply or webhook resume starts a new root trace). Aggregate by anthropic.session.id for full-session cost/outcome analysis and by gen_ai.conversation.id sorted by start time for per-thread transcripts.
  • Normalize across SDK versions & redaction changes: Pin beta SDK versions and annotate dashboards when upgrading Claude Code or agent harnesses so schema or attribution changes (e.g., query_source or mcp_server.name behavior) are not misread as production regressions.
COHORT ANALYSIS

Failure-Cohort Analysis to Surface Systemic Issues

Live Read-Along (click any sentence to jump)
Failure-cohort analysis turns raw traces into prioritized engineering work. Instead of reading random error traces, you slice degraded runs by response model, stop reason, tool name, cache miss reason, prompt version, and tenant. A tiny overall error rate often conceals a forty-percent failure cohort isolated to one MCP server or one prompt revision—giving you both the root cause and a ready-made regression test set.

Failure-cohort analysis groups failed or degraded traces by shared structural attributes to quantify whether an issue is random noise or a systemic fault tied to one slice of traffic. Start from an anomaly (e.g., task success dropped 3% or p95 latency jumped 2x), then pivot and compute failure rates across cohorts: gen_ai.response.model, anthropic.message.stop_reason, error.type, cache_miss_reason.type, tool name (anthropic.mcp_tool_use <tool>), prompt/skill version, deployment.environment, and tenant.

For example, an overall 1.2% tool-failure rate looks benign until cohort slicing reveals a 42% timeout rate confined to one MCP server on requests carrying >100k input tokens, or a 60% max_tokens truncation rate isolated to a newly deployed skill version. Quantifying cohort size and blast radius lets you prioritize fixes and feed exact failing cohorts into Domain 5 regression eval suites.

EXAM TRAP

Averages Hide Localized Cohorts; Head Sampling Blinds Tail-Event Diagnosis

Live Read-Along (click any sentence to jump)
On the exam, watch for two classic mistakes in trace analysis. Never trust fleet-wide averages that blend models, tools, and tenants together—always slice into failure cohorts. And never fix missing rare-error traces by cranking head-based sampling to one hundred percent when tail-based sampling can keep every error and latency outlier at a fraction of the ingestion cost.

Two recurring CCDV-P exam traps in Trace Analysis at Scale: (1) Concluding a service is healthy because fleet-wide p50 latency or aggregate error rate looks flat—always stratify by model, tool, stop reason, and tenant cohort. (2) Attempting to debug a rare 0.5% multi-turn failure by raising global head-based sampling to 100% (which blows up collector costs) instead of deploying tail-based sampling that captures 100% of error, high-latency, and anomalous stop-reason traces while sampling healthy traffic at 1–5%.

Scenario 1: HIPAA Telemetry & Token Double-Counting

A healthcare SaaS team running on a HIPAA-enabled Claude API organization configures both Anthropic SDK OpenTelemetry tracing and a Claude Console API telemetry destination set to Full content so they can debug tool-runner loops and reconcile daily token spend. After rollout, two issues appear: (1) their observability dashboard reports roughly double the actual token usage on successful Messages API calls, and (2) API server spans contain no prompt or response text despite Full content being enabled on the destination. What is the root cause and best fix for both issues?

Answer: B — When both SDK (CLIENT) and API (SERVER) tracing are enabled, both emit an anthropic.messages.create span with token counts; summing both doubles totals. You must sum only one source (API SERVER spans capture billed tokens even on aborts, deduplicated by trace_id + span_id, and the Usage & Cost Analytics API is authoritative for billing). Second, for organizations with HIPAA, FERPA, or K-12 restrictions, Claude API telemetry destinations automatically export metadata only regardless of the Full content setting, whereas SDK spans inside the customer's own environment are unaffected. Option A misattributes missing content to the 0.75 MB limit (which sets anthropic.content.truncated=true rather than omitting all content) and loses client-side tool visibility. Option C is wrong because HIPAA readiness does not require ZDR and ZDR does not override HIPAA destination metadata-only enforcement; also subtracting cache reads from gen_ai.usage.input_tokens undercounts total input tokens. Option D is wrong because Managed Agents is not HIPAA-eligible and summing both create and model_request spans double-counts tokens.

Scenario 2: Silent Cost Surge and Cache-Hit Collapse

A multi-turn document-analysis agent uses the Messages API with prompt caching. After a routine deployment, HTTP 200 availability remains at 99.98%, yet hourly spend in the Usage and Cost Analytics API jumps 3.5x and p95 time-to-first-chunk doubles. Telemetry shows usage.cache_read_input_tokens has dropped near zero on turns 2 through 8, while usage.cache_creation_input_tokens spiked. The team enables Cache Diagnostics by threading previous_message_id across turns and sees diagnostics.cache_miss_reason.type returning 'system_changed' on turn 2. What most likely caused the incident and what is the right remediation?

Answer: B — Cache Diagnostics identifies the earliest point of prefix divergence. Returning 'system_changed' specifically proves the system parameter differs byte-for-byte from the previous turn—most commonly caused by interpolating a dynamic timestamp, request ID, or session variable into the system prompt. Keeping the system prompt constant and placing per-turn dynamic data in the appended user message restores cache hits. Option A would show diagnostics: null with zero cache reads (matching prefix, expired entry). Option C would report 'tools_changed', and Option D would report 'model_changed'.

Scenario 3: Isolating a Rare Multi-Agent Failure Cohort at Scale

A production support platform runs 40,000 multi-turn Agent SDK sessions per hour across 12 tenants and 8 MCP servers. To control observability costs, the platform uses 2% head-based OpenTelemetry sampling. Over the past week, customer complaints indicate roughly 0.9% of billing-dispute tickets silently end with incomplete answers, yet fleet-wide HTTP error rates and p50 latency look normal, and engineers rarely find a failing trace in their backend. Which observability architecture change will most effectively surface and quantify the root cause without blowing up telemetry costs?

Answer: C — With 2% head-based sampling, 98% of a 0.9% failure mode is discarded before the trace even finishes. Trace-ID-aware tail-based sampling in the OTel Collector keeps 100% of anomalous traces (errors, latency outliers, max_tokens/refusal stops, tool failures) while sampling healthy traffic at 2%, keeping costs bounded. Slicing those captured traces into failure cohorts by response model, stop reason, MCP server, and tenant quantifies whether the 0.9% issue is a concentrated systemic fault (e.g., one MCP server or tenant). Option A explodes storage/egress costs and risks capturing sensitive raw bodies unnecessarily. Option B causes catastrophic Prometheus cardinality explosions (unbounded IDs belong on traces/events, not metric labels). Option D breaks the Agent SDK because the console exporter writes to stdout, corrupting the CLI-to-SDK pipe.
