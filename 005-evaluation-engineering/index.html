Evaluation System Design

Offline Eval Architecture, Graders, and Agent Non-Determinism

KEY CONCEPT

Anatomy of an Agent Evaluation

Live Read-Along (click any sentence to jump)
When you evaluate an AI agent, you are never testing the model in isolation. You are testing the model and its agent harness together. Each test case is a task, and each run is a trial executed in a clean, isolated environment. Crucially, graders should distinguish between the transcript, which is the full messages array, and the outcome, which is the actual final state in the database or file system.

An agent evaluation measures the model and agent harness working together across multi-turn loops. Each task defines inputs and unambiguous success criteria, and each attempt is a trial run inside an isolated environment. Graders score two distinct artifacts: the transcript (the complete messages array of tool calls, reasoning, and outputs) and the outcome (the verified final state in the environment, such as a database row or generated file).

EXAM TRAP

Grade Outcomes, Not Rigid Tool-Call Sequences

Live Read-Along (click any sentence to jump)
Watch out for a classic exam trap: grading the exact sequence of tool calls instead of the final outcome. Frontier models often find creative, valid paths that rigid sequence checks unfairly fail. Also, never share state between trials. Leftover files or git history can cause correlated failures or let the model cheat. Always verify every task with a reference solution, because a zero percent pass rate across many trials usually means your task spec is broken.

A common anti-pattern is asserting an exact sequence of tool calls. Frontier models frequently discover valid, unanticipated paths to solve a task, so path-based assertions create brittle false failures. Equally dangerous is shared state across trials (leftover files, cached data, or git history from prior runs), which causes correlated flakiness or lets the agent cheat. Always isolate every trial and include a reference solution; a 0% pass@100 rate almost always signals a broken task spec or grader bug, not an incapable model.

ARCHITECTURE PATTERN

Capability vs. Regression Suites and Balanced Problem Sets

Live Read-Along (click any sentence to jump)
Separate your offline evaluations into two suites. Capability evals start with a low pass rate on hard problems to give your team a hill to climb. Regression evals sit near one hundred percent to catch backsliding, and mature capability tasks graduate into them over time. Always keep problem sets balanced with both positive and negative cases so you prevent overtriggering, and start early with twenty to fifty tasks pulled from real failures.
  • Capability (Quality) Evals: Start at a low pass rate on hard tasks the agent currently struggles with, giving teams a clear hill to climb and revealing which bets pay off on new model releases.
  • Regression Evals: Maintain a near-100% pass rate on proven behaviors to catch backsliding before release. High-performing capability tasks should graduate into the regression suite.
  • Balanced Problem Sets: Test both positive triggers (when a tool or skill should fire) and negative controls (when it should not). One-sided suites cause overtriggering—such as searching the web for static facts.
  • Start Small and Real: 20–50 unambiguous tasks sourced from manual release checks, bug trackers, and support tickets beat waiting months for a massive synthetic dataset.
DECISION MATRIX

Choosing the Right Grader Type

Live Read-Along (click any sentence to jump)
Choose the fastest, most reliable grader that fits the task. Start with code-based graders like unit tests, regex checks, and database state verification whenever possible because they are cheap and deterministic. Bring in model-based graders for open-ended nuance, but only after calibrating them against humans. Reserve human subject matter experts for calibration sets and high-stakes spot checks, and build partial credit into multi-step tasks.

KEY METRIC

Measuring Non-Determinism: pass@k vs. pass^k

Live Read-Along (click any sentence to jump)
At k equals one, pass at k and pass to the k are identical, but as you run more trials, they tell opposite stories. Pass at k measures the odds of getting at least one success in k attempts, which rises toward one hundred percent and fits tools where one working draft is enough. Pass to the k measures the odds that all k trials succeed. At a seventy-five percent per-trial rate, pass to the three drops to forty-two percent, making it the right bar for customer-facing consistency.

Because agents are non-deterministic, a single trial is noisy. Two complementary multi-trial metrics capture reliability:

  • pass@k — Probability of getting at least one correct solution in k attempts. Rises toward 100% as k grows. Best for coding or research tools where one valid candidate is enough.
  • pass^k — Probability that all k trials succeed. Falls exponentially as k grows (e.g., a 75% per-trial success rate yields 0.75³ ≈ 42% for pass^3). Essential for customer-facing agents where users expect consistent correctness every single time.
CODE PATTERN

Multidimensional Agent Eval Definition

Live Read-Along (click any sentence to jump)
In production, a single task usually combines multiple graders. Here, a support refund eval verifies the database outcome with a state check, confirms identity verification and refund bounds through tool-call checks, evaluates policy grounding with an LLM rubric, and enforces a ten-turn transcript cap while tracking token and latency metrics.
graders:
  - type: state_check
    expect:
      tickets: { status: resolved }
      refunds: { status: processed }
  - type: tool_calls
    required:
      - { tool: verify_identity }
      - { tool: process_refund, params: { amount: "<=100" } }
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Response is grounded in fetch_policy tool results"
  - type: transcript
    max_turns: 10
tracked_metrics:
  - { type: transcript, metrics: [n_turns, n_toolcalls, n_total_tokens] }
  - { type: latency, metrics: [time_to_first_token, time_to_last_token] }
Evaluation System Design

CI/CD Gates, Groundedness Metrics, and Suite Validity

CODE PATTERN

Gating Releases in CI/CD with Pinned Models and Cost Ceilings

Live Read-Along (click any sentence to jump)
When wiring evals into CI/CD, pin both the agent model and the judge model so an upstream model update is never confused with a code regression. Set a pass threshold, a maximum dollar cost ceiling, and JSON output for archiving. Exit code zero passes the gate, exit code one fails on a regression or error, and exit code two flags a partial run that you must exclude from quality trend charts.
claude plugin eval . \
  --trust-plugin \
  --json results.json \
  --threshold 0.8 \
  --model claude-sonnet-5 \
  --judge-model claude-haiku-4-5 \
  --no-publish \
  --max-cost-usd 20

In CI, always pin both --model and --judge-model so an upstream model rollout is never mistaken for a prompt or plugin regression. Gate builds on exit codes: 0 means all cases met --threshold, 1 signals a threshold failure or run/API error, and 2 signals a partial run (such as hitting --max-cost-usd or an auth failure), which must be excluded from historical trend charts.

ARCHITECTURE PATTERN

Ablation Baselines and Fair Two-Arm Scoring

Live Read-Along (click any sentence to jump)
A high score by itself doesn't prove your plugin or prompt change added value, because Claude might pass the task without it. Two-arm ablation runs every case with and without the change to measure delta. Checks that can never pass in the baseline arm, like invoking a plugin skill, are excluded from scoring in both arms so they don't artificially inflate the lift.

A high absolute score alone does not prove a prompt change, skill, or plugin actually helped—Claude may have succeeded without it. Tools like claude plugin eval run a two-arm ablation (WITH vs. W/OUT) to measure incremental lift (Δ). To avoid artificially inflating Δ, checks that can only pass in the with-arm (such as tool_used: Skill) are reported as pass/fail indicators with scored: false in both arms, while fast inner-loop CI checks can use --ablation none and deterministic-only graders to keep costs predictable.

KEY CONCEPT

Retrieval Precision, Groundedness, and Hallucination Controls

Live Read-Along (click any sentence to jump)
For retrieval-grounded and research agents, evaluate retrieval precision and source authority separately from synthesis quality. Measure groundedness to verify every claim maps to retrieved evidence, and coverage to confirm key facts aren't missed. To curb hallucinations, allow Claude to admit uncertainty, extract direct quotes first on long documents, and verify citations. For strict schema consistency, rely on Structured Outputs rather than prefilling, which is not supported on Claude four point six and later.
  • Retrieval Precision & Source Quality: Verify that retrieved chunks are relevant and authoritative, not merely the top-ranked results, separating retrieval failures from generation failures.
  • Groundedness & Coverage: Check that every factual claim in the output is supported by retrieved evidence (groundedness) and that all required key facts are present (coverage).
  • Hallucination Minimization in Prompts & Evals: Explicitly permit Claude to say "I don't know", require word-for-word quote extraction before synthesizing long documents (>20k tokens), and verify each claim against a supporting quote—retracting unsupported claims.
  • Consistency Enforcement: Use Structured Outputs for guaranteed JSON schema compliance rather than relying solely on prompt formatting or prefilling (note: response prefilling is not supported on Claude 4.6 and later models).
EXAM TRAP

Maintaining Suite Validity: Saturation, Contamination, and Coverage Gaps

Live Read-Along (click any sentence to jump)
Static eval suites lose validity over time in three ways. First, saturation: once scores approach one hundred percent, you lose signal for measuring real capability gains and need harder agentic tasks. Second, contamination or overfitting to a small golden set makes offline scores look great while production stagnates. Third, coverage gaps and grading bugs hide behind summary numbers, which is why reading transcripts is non-negotiable.

An evaluation suite degrades if left static:

  • Saturation: Once an agent scores near 100%, the suite still catches regressions but provides zero signal for capability improvement (as seen when SWE-bench Verified passed 80%, or when one-shot coding evals masked agentic gains). Add harder, longer-horizon tasks.
  • Contamination & Leakage: Benchmark tasks leaking into training data or prompts overfitted to a small golden set inflate offline scores while production quality stagnates. Maintain held-out test sets and refresh cases from live traffic.
  • Coverage Gaps & Transcript Review: Never take scores at face value without reading transcripts. Audits of benchmarks like CORE-Bench and METR revealed rigid float formatting and threshold misconfigurations that unfairly penalized correct agents.
RELEASE CRITERIA

Release Gate Strategy Across Change Types

Live Read-Along (click any sentence to jump)
Match your release criteria to the risk of the change. Run fast deterministic regression suites on every pull request for prompt edits. For model version upgrades, run the full regression and capability suites, check pass to the k consistency alongside latency and token budgets, and re-verify your judge calibration. For harness or tool changes, test in isolated sandboxes with end-state checks and strict turn caps.

LLM-as-Judge Engineering

Calibrating LLM Judges, Rubrics, Bias Mitigation, and Drift

KEY CONCEPT

Calibrate Against Human Labels Before Granting Gating Authority

Live Read-Along (click any sentence to jump)
Never let an uncalibrated LLM judge gate production releases. Treat the judge like a measurement instrument: validate it against a human-labeled golden dataset first. If the judge agrees with human raters only slightly better than a coin flip, you must withhold gating authority until you fix the bias, tighten the rubric, and prove acceptable agreement.

An LLM-as-judge is a measurement instrument, not ground truth. Before allowing a model-based grader to gate CI/CD releases, you must calibrate it against a human-labeled golden dataset and verify that its verdicts align closely with subject matter experts. If a judge agrees with human raters only slightly better than chance, its verdicts are untrustworthy—withhold gating authority until bias is controlled and agreement meets your acceptance bar.

RUBRIC ENGINEERING

Designing High-Signal Judge Rubrics

Live Read-Along (click any sentence to jump)
Strong rubrics make or break LLM-as-judge reliability. Define explicit pass and fail conditions or anchored one-to-five scales, and isolate one judge call per evaluation dimension instead of asking one prompt to score everything at once. Always give the judge an Unknown option when evidence is missing, and enable thinking on the judge model so it reasons carefully before emitting its final score.
  • Concrete PASS/FAIL or Discrete Scales: Instruct the judge to output binary labels (correct/incorrect) or an anchored 1–5 Likert scale rather than open-ended prose.
  • One Dimension per Judge: Decompose complex quality into separate rubrics (e.g., groundedness, tone, completeness) and grade each dimension with an isolated LLM-as-judge rather than bundling everything into a single prompt.
  • Give the Judge an Escape Hatch: Explicitly allow the judge to return Unknown when context is insufficient, preventing hallucinated verdicts.
  • Enable Reasoning Before Scoring: Turn on thinking on the judge model so it reasons through the evidence before emitting the final verdict, and keep judged excerpts concise (use regex graders for long generated files).
BIAS MITIGATION

Diagnosing and Controlling LLM-as-Judge Biases

Live Read-Along (click any sentence to jump)
LLM judges exhibit predictable biases that can silently break your release gates. Position bias causes pairwise judges to favor whichever answer appears first; fix it by randomizing or swapping response order and requiring consistency. Verbosity bias rewards padded answers, self-preference favors the judge's own model family, and small judge models often fail valid outputs over harmless formatting differences. Always test for these on blind human-labeled pairs.
Bias / Failure ModeSymptom in Eval DataEngineering Mitigation
Position / Order BiasPairwise judge favors whichever response appears first (or last) far more often than humans doRandomize or swap A/B presentation order across dual runs; count a win only when consistent across both orders, then re-measure human agreement
Verbosity BiasJudge systematically rewards longer, more padded answers over concise, accurate onesExplicitly penalize fluff in the rubric, test concise vs. verbose pairs in calibration, and separate length-independent factual assertions
Self-Preference BiasJudge favors outputs generated by its own model family or stylistic patternsCalibrate against blind human labels; use a stronger or distinct judge model or multi-judge consensus
Format SensitivitySmall judge marks valid answers wrong due to minor formatting differencesUpgrade judge model (e.g., --judge-model sonnet), tighten rubric to ignore incidental formatting, and use 2-of-3 majority voting
KEY METRIC

Inter-Rater Reliability (Cohen's Kappa) and Human Consensus

Live Read-Along (click any sentence to jump)
Raw percent agreement can fool you on imbalanced datasets, so track chance-corrected inter-rater reliability like Cohen's kappa. Measure kappa both between your human annotators and between your LLM judge and human consensus. If two domain experts disagree on whether a response passes, stop tuning the judge—your task specification or rubric is ambiguous and needs to be rewritten.

Raw percent agreement can be misleading when classes are imbalanced (a judge that always outputs PASS gets 90% agreement on a 90%-pass set). Use chance-corrected metrics like Cohen's kappa (κ) to measure both human-to-human inter-annotator agreement and judge-to-human agreement. If two human domain experts cannot independently reach the same pass/fail verdict on a task, the task specification or rubric itself is ambiguous and must be refined before tuning the judge.

PRODUCTION OPERATIONS

Detecting and Controlling Judge Drift Across Model Versions

Live Read-Along (click any sentence to jump)
Judge drift happens when an updated judge model becomes stricter or more lenient, creating phantom regressions or false passes even though your application didn't change. Prevent drift by pinning exact judge model versions in CI, re-running your fixed human calibration set before adopting any new judge model, and auditing periodic human spot checks against judge verdicts.

Just as application behavior shifts across model updates, judge behavior drifts when the underlying judge model version changes or when rubrics evolve—producing phantom regressions or inflated pass rates even when the candidate agent did not change. Pin exact judge model IDs in CI, re-run your fixed human-labeled calibration benchmark whenever upgrading the judge model, and monitor judge pass-rate distributions and human spot-check kappa over time.

CODE PATTERN

Order-Swapped Pairwise Judge with Thinking Enabled

Live Read-Along (click any sentence to jump)
This Python pattern eliminates pairwise position bias in two calls. It runs the judge with adaptive thinking enabled, first with candidate A in position one and then swapped with candidate B in position one. A candidate only wins if it is selected in both orders; if the verdicts flip, the pair is flagged as a tie or position-inconsistent result.
def judge_pair_debiased(prompt: str, resp_a: str, resp_b: str) -> str:
    def run_once(first: str, second: str) -> str:
        msg = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=2048,
            thinking={"type": "adaptive"},
            messages=[{"role": "user", "content": f"""Compare Candidate 1 and Candidate 2.
Ignore length and formatting; judge factual accuracy and rubric adherence only.
Output '1', '2', 'tie', or 'unknown' in <verdict> tags.
<prompt>{prompt}</prompt>
<candidate_1>{first}</candidate_1>
<candidate_2>{second}</candidate_2>"""}],
        )
        return extract_verdict(msg)

    v1 = run_once(resp_a, resp_b)          # A first, B second
    v2 = run_once(resp_b, resp_a)          # B first, A second
    if v1 == "1" and v2 == "2": return "A"
    if v1 == "2" and v2 == "1": return "B"
    return "tie_or_inconsistent"           # Position-biased disagreement
Online Quality Measurement

Live-Traffic Sampling, A/B Testing, Feedback Loops, and Task Metrics

ARCHITECTURE PATTERN

The Swiss Cheese Model of Production Quality

Live Read-Along (click any sentence to jump)
Think of production quality assurance as the Swiss Cheese Model: no single layer catches every bug, so you stack defenses. Automated offline evals guard CI/CD before launch. Production monitoring catches real-world distribution drift. Shadow evaluations and A/B tests validate major changes safely. Weekly transcript reviews, user feedback triage, and periodic human studies close the remaining blind spots.

No single evaluation layer catches every failure. Like the Swiss Cheese Model in safety engineering, mature Claude teams layer six complementary methods: automated offline evals in CI/CD (fast, pre-launch defense), production monitoring (real-world drift and error detection), shadow evaluation and A/B testing (controlled live validation), user feedback (thumbs-down and bug reports), weekly manual transcript review (qualitative intuition), and periodic systematic human studies (gold-standard calibration).

ONLINE TECHNIQUES

Live-Traffic Sampling and Shadow Evaluation

Live Read-Along (click any sentence to jump)
Online evaluation brings your graders to real traffic. Use stratified live-traffic sampling to run calibrated judges asynchronously across representative requests, oversampling high-risk cohorts and long-turn sessions. Before exposing users to a new model or prompt, run shadow evaluations that replay real inputs in the background so you can measure latency, cost, and quality on true production distributions with zero user impact.
  • Stratified Live-Traffic Sampling: Run asynchronous online evaluators (deterministic checks and calibrated LLM judges) on a representative sample of production traces, oversampling high-risk cohorts, long-turn sessions, and tool-error traces to detect distribution shift without blowing up cost.
  • Shadow Evaluation: Replay live production inputs against a candidate prompt, model, or harness in the background without returning its output to users—measuring latency, token cost, schema validity, and judge scores on real traffic distribution with zero user impact.
  • Privacy-Safe Capture: Apply PII redaction and zero-data-retention policies before sampling traces into offline evaluation datasets.
TRADE-OFFS

A/B Testing vs. User Feedback Loops

Live Read-Along (click any sentence to jump)
Know the trade-offs between A/B tests and user feedback. A/B tests control for confounds and measure real user outcomes like task completion and retention, but they take days or weeks to reach significance and don't tell you why a metric moved until you read the transcripts. Explicit thumbs-down feedback surfaces real edge cases, yet it is sparse and self-selected, so pair it with implicit signals like retries and escalations.

A/B testing measures actual user outcomes (task completion, retention, escalation rate) while controlling for confounds, but it is slow (requiring days or weeks and sufficient traffic to reach statistical significance) and reveals what changed without explaining why—always pair A/B deltas with transcript review. Explicit user feedback (thumbs-down, bug reports) surfaces unanticipated edge cases with real examples, but it is sparse, self-selected, and skews toward severe failures; combine it with implicit signals (retries, abandonment, edits, human escalations).

METRIC SELECTION

Matching Evaluation Metrics to Task Type

Live Read-Along (click any sentence to jump)
On the exam, match your metrics tightly to the task type. For extraction and classification, use exact match, F1, and schema compliance. For open-ended generation, use calibrated rubric scores and user acceptance rates. For agentic workflows, prioritize verified end-state outcomes, pass to the k consistency, and turn or cost efficiency. For retrieval-grounded systems, measure retrieval precision, claim groundedness, citation accuracy, and proper abstention.

CLOSING THE LOOP

Eval-Driven Development: Turning Production Failures into Regression Tests

Live Read-Along (click any sentence to jump)
Finally, close the loop with eval-driven development. Every time live-traffic sampling, a thumbs-down report, or a weekly transcript review reveals a new failure mode, convert that redacted example into an unambiguous offline regression test with a reference solution. That way, every production incident strengthens your CI gate permanently.

The highest-leverage operational habit in evaluation engineering is closing the loop between production and CI/CD. Every time online monitoring, a user report, or a weekly transcript review uncovers a novel failure mode, convert that redacted trace into an unambiguous, balanced test case with a reference solution and add it to the offline suite. Over time, failures compound into permanent institutional memory—turning reactive firefighting into predictable, metric-driven releases.

Production Scenario Questions

Scenario 1: Brittle Agent Evals and Hidden Non-Determinism

A platform team is preparing to upgrade their customer-facing billing support agent to a newer Claude model. Their offline eval suite runs each of 60 tasks once (k=1) and asserts that the agent invokes `lookup_account`, `fetch_policy`, and `issue_credit` in that exact order. After the upgrade, the suite pass rate drops from 92% to 74%, yet manual spot checks show the new model resolves tickets accurately by calling `fetch_policy` and `lookup_account` in parallel. Meanwhile, customers on the current version report intermittent failures where identical refund requests succeed on one attempt and fail on the next. Which combination of changes best fixes their evaluation methodology?

Answer: B — B addresses both root issues: grading rigid tool-call sequences penalizes valid parallel or creative agent paths (grade outcomes and required preconditions instead), and running k=1 hides non-deterministic flakiness that hurts customer-facing agents—pass^k directly measures the probability that all k trials succeed consistently. A enforces a brittle path and uses pass@5, which measures at least one success rather than consistency; C bundles multiple dimensions into one uncalibrated LLM judge and keeps k=1; D masks real regressions by deleting failing tests.

Scenario 2: Uncalibrated Pairwise Judge and Judge Drift

An engineering team uses a pairwise LLM-as-judge in CI/CD to gate weekly prompt updates by comparing the candidate response (always placed first) against the production baseline (always placed second). After upgrading the judge model to a smaller, faster model to reduce CI spend, candidate pass rates jump from 58% to 94%, yet production CSAT drops over the next two releases. Auditing 100 human-labeled pairs reveals the new judge has a Cohen's kappa of 0.14 with SMEs and picks whichever candidate appears first 81% of the time. What should the team do first?

Answer: A — A directly resolves both judge drift and severe position bias (81% first-position preference, kappa 0.14): an uncalibrated judge cannot safely gate releases, so the team must suspend gating authority, control position bias via order randomization/swapping, pin a calibrated judge model, and verify acceptable Cohen's kappa against human labels first. B merely shifts the threshold on a broken signal; C relies on a prompt-only plea without measuring or fixing calibration; D changes the scoring format without validating agreement on the smaller judge.

Scenario 3: Offline Saturation vs. Live Retrieval-Grounded Failures

A financial research assistant powered by Claude maintains a 99% pass rate on its 120-task offline regression suite. Despite green CI builds, enterprise customers report that answers to recent regulatory filings increasingly contain unsupported numbers and fail to admit when a filing lacks the requested metric. Investigation shows the offline golden set has not been updated in nine months and only checks exact-match answers on older filings. Which strategy best restores quality assurance?

Answer: C — C applies the Swiss Cheese Model to fix suite saturation and coverage gaps: live-traffic sampling with task-matched retrieval-grounded metrics (groundedness, citation verification, abstention on unanswerable queries) detects real-world drift immediately, transcript review diagnoses failure modes, and feeding balanced new-filing and unanswerable cases back into the offline suite restores CI signal. A tightens a saturated, stale suite; B exposes users directly to untested regressions and is too slow for per-commit gating; D optimizes length on stale tasks without measuring groundedness or abstention.
